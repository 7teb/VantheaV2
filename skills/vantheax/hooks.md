# Hooks

A hook is a shell command that VantheaX runs automatically at a fixed point of a turn: before or after a tool call, when a message is sent, when a turn or a sub-agent finishes, when a turn fails, when a sub-agent starts. The model follows Claude Code's hooks (events, a matcher, the event as JSON on stdin, exit codes, JSON output), adapted to VantheaX's tools. VantheaX has no other hook handler types: no HTTP, prompt or agent hooks, no async hooks.

## Where hooks live

Hooks are stored only in VantheaX's own `settings.json` under `%APPDATA%\VantheaX\v2`, in two scopes: global hooks ("All projects" / "Alle Projekte") run in every chat, project hooks run only in chats of that project (a worktree chat uses the hooks of its project). A chat without a project gets only the global hooks. VantheaX never reads hooks from a file inside a project folder, `.claude/settings.json` included, so a cloned repository cannot plant commands that run automatically. When a project folder moves, its hooks follow it; removing a project removes its hooks. A hook added or changed while a turn runs applies from the next matching event on.

## Settings > Hooks and /hooks

Settings > Hooks (in the Integrations group, after MCP servers) lists the hooks grouped by scope, each row with the event, the matcher ("All tools" / "Alle Tools" when it is empty), the shell, the timeout, the command, an on/off switch, Edit ("Bearbeiten") and Remove ("Entfernen", asks first). "Add hook" ("Hook hinzufügen") next to the heading opens the dialog with Event ("Ereignis"), the matcher (labelled Tool name, Agent type or Error kind, hidden for events without one), Shell (PowerShell or Git Bash), Command ("Befehl"), "Timeout (seconds)" ("Zeitlimit (Sekunden)", 1 to 3600, default 60), Enabled ("Aktiv") and "Applies to" ("Gilt für": All projects or one project). Hooks the user creates or edits here need no approval. The "/" command Hooks opens this section. A paired phone can add and change hooks the same way it can add MCP servers.

## Events

Every event gets one JSON object on stdin, written once and then closed. All characters above U+007E are written as `\uXXXX` escapes, so the JSON is plain ASCII and decodes the same in Windows PowerShell, Git Bash, jq, Python and Node. Common fields: `session_id` (the chat id), `turn_id` (the assistant message of the turn, or the sub-agent's run id), `hook_event_name`, `cwd` (the folder the hook runs in: the chat's project folder, its worktree folder, or the workspace folder of a chat without project; a sub-agent's own folder), `project_path` (the chat's project, empty without one), `permission_mode` (`ask`, `auto` or `full`; an open 10-minute window reads as `full`), `plan_mode`, `agent_type` (`main`, `explore` or `worker`) and, for sub-agents and workflow agents, `agent_id` and `agent_name`.

- UserPromptSubmit: before a turn that starts with a message the user sent (a typed message, Initialize, Create GitHub repository or Review) and for every steer typed into a running main-agent turn; turns the app starts itself (Continue, accepting a plan, Undo, background task events, agent reports and updates, workflow results) do not run it. Fields `prompt` and `origin` (`user`, `init`, `git_init`, `review` or `steer`). No matcher. Plain stdout on exit 0 and `hookSpecificOutput.additionalContext` go to the model as context after the message. Exit 2 (stderr is the reason) or `decision: "block"` with `reason` blocks the message: at the start of a turn the turn ends with the error card "A hook blocked this message." ("Ein Hook hat diese Nachricht blockiert.") and the reason under Details; a blocked steer is not delivered and shows as a hook row "A hook blocked a message" with the text and the reason. The model never sees a blocked message, its title is not generated from it, memory does not scan it, and the review does not count it as a user request. A message whose turn the user stops while its UserPromptSubmit hooks still run is treated the same way.
- PreToolUse: before a tool call runs, after the tool row appears and before any review or approval card, for the main agent and sub-agents. Fields `tool_name`, `tool_input`, `tool_use_id`; an MCP call is described as `mcp__<server>__<tool>` with its own arguments and `mcp_server: { name }`. It can only block: exit 2, `hookSpecificOutput.permissionDecision: "deny"` with `permissionDecisionReason`, or the older `decision: "block"` with `reason`. `allow`, `ask`, `defer`, `updatedInput` and `additionalContext` are read but change nothing. A blocked call does not run; it shows as that tool's own row in its blocked state ("Blocked <target>" / "<target> blockiert"), the hook and its reason in the row's body, and the model is told the user's hook blocked it and not to get around it.
- PostToolUse: after a tool call succeeded (a command that moved to the background counts). Fields `tool_name`, `tool_input`, `tool_use_id`, `tool_response` (`status`, `text` as the model got it, `view`) and `duration_ms`. `hookSpecificOutput.additionalContext`, `decision: "block"` with `reason`, or exit 2 with stderr put the text in front of the tool result the model reads; plain stdout is ignored.
- PostToolUseFailure: after a tool call failed (not after a denial or a stop). Fields as PostToolUse, with `error` instead of `tool_response`. Output as PostToolUse.
- Stop: when a main-agent turn is about to end normally (not on the user's Stop and not on an error). Fields `stop_hook_active` (true when the last continuation came from a Stop hook and the model made no tool call since) and `last_assistant_message`. No matcher. `decision: "block"` with a `reason` (required), exit 2 with stderr, or `additionalContext` keep the turn going: the text goes to the model as a note and it runs another round. There is no limit on how often; a script should check `stop_hook_active`, and the user's Stop always ends the turn. When the provider ended the answer with its content filter, the hook still runs but cannot keep the turn going.
- SubagentStop: the same for a sub-agent's run; its report is delivered when the run really ends. Matcher: the agent type.
- StopFailure: when a turn ends with an error, before the error card. Fields `error` (the error kind: rate_limited, provider_unavailable, stream_interrupted, timeout, context_limit, policy, auth, credits, bad_request, internal) and `error_details`. Matcher: the error kind. Its exit code and output are ignored; only a timeout or a hook that cannot start shows.
- SubagentStart: once when a sub-agent run starts. Matcher: the agent type (`explore`, `worker`). `additionalContext` goes to the sub-agent after its task. It cannot block; exit 2 shows stderr to the user only.

## Matchers

The matcher picks the tool name for PreToolUse, PostToolUse and PostToolUseFailure, the agent type for SubagentStart and SubagentStop, and the error kind for StopFailure; UserPromptSubmit and Stop ignore it. Empty or `*` matches everything. Only letters, digits, `_`, `-`, spaces, `,` and `|` means exact names, for example `run_command|run_bash` or `write_file, replace_in_file`. Anything else is a JavaScript regular expression, not anchored and case-sensitive: `write` matches write_file, `^write_file$` only that tool, `mcp__ida-pro__.*` every tool of the MCP server ida-pro; `mcp__ida-pro` alone is an exact name and matches nothing. VantheaX's tool names include run_command (PowerShell), run_bash (Git Bash), start_background_task, read_file, write_file, replace_in_file, list_files, grep_files, get_file_outline, web_search, deploy_agent, continue_agent, message_agent, run_workflow, ask_user, present_plan, update_todos, the browser_ tools, load_mcp_tools, list_hooks, save_hook and delete_hook.

## Exit codes and JSON

- Exit 0: success. When stdout (trimmed) starts with `{` and ends with `}` it is read as one JSON object; the fields above apply. Stdout that looks like JSON but does not parse, or a field with the wrong type, is a hook error ("Invalid JSON output" / "Ungültige JSON-Ausgabe"). Any other stdout is plain text, which counts only on UserPromptSubmit. Stderr is ignored.
- Exit 2: blocks where the event can block (see above); stderr is the reason ("No reason given" / "Kein Grund angegeben" when it is empty). JSON fields are read but cannot undo the block.
- Any other exit code: a hook error that blocks nothing, its stderr shown; valid JSON on stdout still decides.
- The JSON fields `continue`, `stopReason`, `systemMessage`, `suppressOutput`, `updatedInput` and `updatedToolOutput` are accepted and ignored.

Several hooks on one event run at the same time and all finish; a block from any of them wins and the context of all of them is kept. Two hooks with the same shell and the same command (also one global and one in the project) run once.

## Running

A hook runs in the chat's folder (`cwd`) through the same PowerShell or Git Bash VantheaX uses for run_command and run_bash, without the command review, because the user created or approved it. PowerShell: read the event with `$e = [Console]::In.ReadToEnd() | ConvertFrom-Json`, write a reason with `[Console]::Error.WriteLine('...')` and end with `exit 2`. Git Bash: read it with `cat` (or `jq`) and write the reason with `echo ... >&2; exit 2`. A Git Bash hook on a PC without Git Bash fails with "Could not start" ("Konnte nicht starten"). Each hook has a timeout (60 s by default, 1 to 3600 s per hook); a hook that times out or cannot start is a hook error and never blocks anything.

## What the user and the model see

A silent success shows nothing. On a tool call, hook output and hook errors are in the expandable body of that tool row, one card per hook ("Hook · PowerShell" with the command, the text, an outcome such as "Blocked the call", "Sent to the model" or "Hook error", and the duration); the row head stays the tool's icon and label. Hooks of the other events show as a hook row in the turn (for example "Stop hook continued the turn", "Message hook added context", "Turn failure hook"), with a red mark when a hook failed, and the hook cards in its body; sub-agent transcripts show them the same way. The model gets only what the hook adds as context or as a reason, attributed to "a hook the user set up" with its command.

## The model's tools

- list_hooks (main agent and plan mode): the hooks of this chat's scopes with id, event, matcher, shell, timeout, on/off and command. No approval.
- save_hook (main agent): without `id` it creates a hook (`scope` global or project, `event`, `shell`, `command`; `matcher`, `timeout_s`, `enabled` optional); with `id` it changes only the fields given, and passing only `enabled` turns a hook on or off. An existing hook keeps its scope. Project scope needs a chat with a project.
- delete_hook (main agent): deletes one hook by id.

A change the model makes follows the permission mode like any other tool call: in Ask mode it waits for the user on an approval card, in Auto and Full mode the automatic review decides with the chat as context and shows the card only when it cannot decide or is unavailable. The card ("May I add this hook?", "May I change this hook?", "May I turn on/off this hook?", "May I remove this hook?"; "Darf ich diesen Hook hinzufügen?" and so on) shows the scope, the event, the matcher, the shell, the timeout and the exact command, for a change the old values, and the review's reason when the review sent it. Sub-agents have none of these tools. A declined change leaves everything as it was, and the model is told not to change hooks another way.
