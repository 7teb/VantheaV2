# Turns, tool rows and the task list

## Turn header and fold

From the first activity item of a turn (reasoning with visible text, a tool call, an intermediate text, a compaction or a notice), a header with a thin line under it sits at the top of the turn, directly under the user message: "Working" ("In Bearbeitung") during the first second, then "Working for 12s" ("In Bearbeitung seit 12s"), counting up every second. Generated images the agent showed with present_images, a visualization or a plan card also keep the header, and a retry that drops the reasoning of the current attempt does not remove it. A turn that only writes answer text gets no header and no line. Times show days, hours, minutes and seconds, leaving out parts that are zero (for example "1h 5s").

When a turn ends as done with answer text, a plan card, generated images shown with present_images or a visualization after its last activity step, everything up to and including that step (reasoning rows, tool rows and groups, intermediate texts, notices, compaction rows) folds behind "Worked for 1m 5s" ("Dauer: 1m 5s") with a chevron, together with reasoning rows without text that sit between that step and the answer. The time runs from the start of the turn to the end of the last tool call (shown generated images, visualizations and the plan included) or reasoning block before the answer; when the last activity step is a compaction or a notice, it runs to the end of the turn. A click opens or closes the activity, and the button stays where it was clicked. The answer text, shown generated images, visualizations, the plan card with its accept question, the user's steering messages, the file card and the action row stay visible. An answer that hit the output limit and was continued stays one answer: both parts stay visible, and the output limit notice between them folds with the activity. A done turn that ends on an activity step without an answer after it does not fold; it keeps a plain "Worked for" ("Dauer") header when it wrote any answer text and has no header when it did not. Failed and blocked turns never fold, follow the same header rule and keep their error at the bottom. A stopped turn always shows "You stopped after 12s" ("Du hast nach 12s gestoppt") as its header, also when it only wrote answer text, and an interrupted one with activity shows "Activity" ("Aktivität"); neither folds.

A turn does not count as finished while a sub-agent it deployed or continued, or a workflow it started, still runs: its header keeps showing "Working for" ("In Bearbeitung seit") with no toggle and everything stays open, also right after switching back to its chat. The turns that agent reports and updates start by themselves join it: they get no header and no line of their own, and their report rows and texts flow on under the same header. Only when the last of these turns is done and no sub-agent of the chain runs any more does the whole chain fold behind one "Worked for" ("Dauer"), timed from the start of the first turn to the end of the last activity before the final answer; then only the final answer, the one file card for the whole chain and the action row stay visible, and the report rows, earlier texts and errors fold with the activity. A message of the user, a background task result or a manual compaction starts a new turn with its own header.

Every finished turn starts folded, also in chats opened later. What the user opened or closed is kept while the app runs, also across chat switches, and is not saved. Sending the next message in a chat folds the turns opened there again. Sub-agent transcripts in the Background Tasks panel do not fold.

## Tool rows and the task list

MCP tools are not sent to the model with every request. The system prompt lists the names of all connected MCP tools, one line per server; the model loads the full definitions it needs with load_mcp_tools (by name, or by a query over names and descriptions) and calls a tool through call_mcp_tool. The list of tools sent to the provider therefore stays the same however many MCP tools are connected, which keeps the prompt cache intact. A load shows as one row "Loaded tools" ("Tools geladen") with the plug icon that does not open; a call shows as the MCP tool's own row, like before. Built-in tools are all sent as before.

Consecutive tool calls of one response that read or look something up, generate images or start agents run at the same time: read_file, list_files, grep_files, get_file_outline, view_image, analyze_image, read_attachment, web_search, generate_image, deploy_agent, continue_agent, get_agent_status, list_agents, get_background_task, list_memories, read_skill, list_models, load_mcp_tools, datetime and context_status. Every other call (edits, commands, background task starts and cancels, browser and check_page steps, MCP calls, memory and skill changes, agent messages, workflows, the task list, questions, plans and shown images) runs on its own and waits for the calls before it, in the order the model wrote them. Each parallel call has its own row with its own running state and result, results reach the model in the order of the calls however they finished, and each call that asks for approval gets its own card. Stop ends all of them; the ones that had finished keep their result.

Each tool call is one row with an icon and a label. Rows show no counts (files, matches, results, agents); what a call found is in its opened body. At its right edge a row adds only a status it shows nowhere else:
- a finished grep_files that found nothing: "No matches" ("Keine Treffer");
- a finished web search that found nothing: "No results" ("Keine Ergebnisse");
- listing hooks or scheduled tasks when there are none: "No hooks" ("Keine Hooks"), "No scheduled tasks" ("Keine geplanten Aufgaben");
- a peer message that was not delivered ("Not running" / "Läuft nicht", "Already sent" / "Schon gesendet");
- the live status of a background task or agent run, in the interface language (a task or run that is no longer in the list, for example after "Clear finished commands" / "Beendete Befehle entfernen", keeps its final status or shows "Ended" / "Beendet").

A web search row reads "Searching the web" / "Searched the web" ("Durchsucht das Web" / "Web durchsucht") followed by the query in a small monospace gray, or "Reading 3 pages" / "Read 3 pages" when it reads URLs. It does not open itself. Once it is done, a second line hangs off its icon with a rounded connector: "Sources" ("Quellen") with the favicons of the first six sources as small overlapping circles, "+2" for more, and a chevron. Clicking it lets the sources come in one by one, each favicon moving from the stack into its row with the title and the domain; a click on a source opens it in the browser. Under the sources sit the URLs that failed (in red) and Tavily's answer when there is one. Clicking again moves them back into the stack. While the turn runs, the connector draws itself and the line fades in from a blur. A failed, denied or cancelled web search keeps the normal tool row.

A failed row does not claim success: its label is in command form ("Edit CHANGELOG.md", "Write 0.4.0.md"), while a command that ran and ended with an exit code keeps "Ran ...". The row carries no extra failure mark. Opened, it shows a short gray error in the interface language instead of the text the model got, for example "The text to replace was not found in CHANGELOG.md. The file was not changed." ("Der zu ersetzende Text wurde in CHANGELOG.md nicht gefunden. Die Datei wurde nicht geändert."), "<path> does not exist in the project", "<path> is outside the project folder", "No Tavily API key is set" or the reply of the service (for example "Tavily 401: ..."); an error without its own short text shows the tool's message. A failed MCP call shows the server's reply without a marker under the arguments of the call. A denied row names its target without the raw tool name ("Denied github · create_issue"); a denial without a reason or feedback cannot be opened, and a denied MCP call shows the same note as a denied command. A command that did not run because a script it runs changed three times during the review opens to "Not run: a script it runs changed three times during the review" ("Nicht ausgeführt: Ein Skript, das er ausführt, hat sich während der Prüfung dreimal geändert"). A tool group's line counts the finished steps, a command that ran counts even when it ended with an exit code, and other failed steps are not counted; denied ones follow as "1 denied" ("1 abgelehnt") in amber. A group whose steps all failed shows the last step's label.

Tool rows and thought rows show no duration. A deployed agent row shows a spinner while the agent runs and no status word; once the run ends it names the outcome. A command that waits for approval reads "Run PowerShell command" ("PowerShell-Befehl ausführen") or "Run Git Bash command" ("Git-Bash-Befehl ausführen"); the command itself is on the approval card. Rows of the running turn fade in, and a new row inside an open group of the running turn grows in from zero height. The icon of a running row is brighter, child rows inside a tool group have the same gray as the group head, and running items use a circle spinner. A label that changes in place does not jump: when a row goes from running to done, a group head changes its text, icon or time, a thought gets its status, the turn header goes from "Working for" to "Worked for" or the task list head moves to the next item, the old text moves up and fades out while the new one comes in from below in 180 ms, and the width follows. Rows, groups, thoughts and folded turns open in 300 ms and close in 200 ms. A failed or timed out command row can be opened to show its card with the exit code. The running command card shows "Running" ("Läuft") at the bottom right until it ends. Reads and skills use an open book, MCP a plug, memory a worm and visualizations a pie chart. A finished tool group shows the icon of its first tool call, which is also the kind its line starts with ("Edited 1 file, ran 1 command" shows the file icon, "Deployed 1 agent, ..." that agent's icon). While a tool group still runs, three purple dots take the place of that icon, and the icon comes back when the group is done. The dots move through five motions: a tilting orbit, a weave in which they bunch up and spread out again, a shuffle in which they swap places, a juggle, and a heartbeat in which they gather, pulse and burst apart. Each spinner unfolds its first, random motion from a single dot in the middle; between motions all three dots gather into that one dot, hold for a moment and unfold into the next random motion, never the same one twice in a row. The user's own messages, steers included, sit in a purple bubble; the send and stop button of the composer (a faded purple while there is nothing to send), the Submit button of a question form and the filled part of the context ring and its popover bar are purple as well. Everything else keeps the gray and white look. Sub-agents have no robot icon: each agent shows a small colored icon picked from its name (the same name always gets the same icon) out of 24: eight 5x5 pixel critters, eight 7x7 pixel critters and eight blooms (flower shapes in one of eight colors). It shows on the agent's tool rows (deploy, continue, status, stop, messages), on its report rows, on "View transcript" and in the agents panel; while that agent runs, a critter hops slightly and a bloom turns slowly. Agent rows without one specific agent (list_agents, a message to the main agent) show a neutral critter in the row color.

Tool calls and the reasoning between them join one tool group per stretch of work, so reasoning no longer splits a group into separate rows. A stretch ends at answer or intermediate text that is not blank, a steer, a visible notice, a compaction, a plan card, generated images shown with present_images or a visualization; hidden tool calls and hidden notices do not end it. Agent reports ("Report from <name>"), agent updates ("Update from <name>") and messages between agents do not end it either: they join the group as rows. This also holds when a report or update arrived after the main agent had ended its turn and so started a new internal turn: its row is shown as the first row of that turn's work, inside the group of the tool calls that follow it. A peer alert in such a turn keeps its own row. A stretch with only one visible step stays a single row (a tool row or a reasoning row), and a stretch of reasoning without any tool call keeps its separate reasoning rows. A group starts closed, also while the turn runs, and keeps what the user opened or closed. A group whose tool calls are all web searches (reading pages included) starts open instead and has no height limit. A group with a running workflow also stays closed; its head names the workflow ("Running workflow <name>") until the workflow ends, and the workflow itself is followed in the Background Tasks panel, see the workflows document. When it is done, its head shows the terminal square, the count sentence of its finished tool calls (for example "Read 2 files, searched 1 string"; reasoning is not counted) with the denied count at the right edge. Group heads show no time. When the sentence does not fit the width of the row, the head keeps as many of its parts as fit and ends with "ran additional tools" ("weitere Tools ausgeführt"), for example "Updated todos, deployed agents, read files, ran additional tools", so the label never runs out of the row half cut. While it runs, the head shows the purple dots and what happens right now: the status of the newest thought while that thought streams, or "Thinking" ("Denkt nach") when it has none yet, otherwise the label of the running tool, or the review label with the shield while a command is being reviewed. When several tool calls of the group run or wait for approval at the same time, the head names the first of them and how many more run alongside, for example "Reading a.ts and 2 more" ("Liest a.ts und 2 weitere"). While the group is open and at least one of its steps has finished, the head shows the count sentence of the finished steps instead, next to the dots. Between two rounds, while the model has not answered yet, the last group of the running turn keeps the dots and says "Thinking" itself; there is no separate "Thinking" line under it then, so nothing jumps when the next thought or tool call joins the group. Every head label stays at least 650 ms before the next one replaces it. Approval cards show below the head, so they stay visible while the group is closed. The open group lists its tool rows and one row per thought in order, in a box at most min(18rem, 50vh) tall that scrolls with a thin scrollbar and faded edges while there is more to scroll. Each row hangs off a thin line at the left with a small rounded connector, and with a mouse the chevron of a closed row in the group shows only while the pointer is on it. While the turn runs and the box is scrolled to its bottom, it stays at the bottom as rows are added or grow; once the user scrolled up or clicked a row in it, it stays where it is until the user scrolls back to the bottom. A thought row has a small dot in place of an icon, the thought's description (see Reasoning row) in the same gray as the tool rows, and a chevron that opens the full reasoning text; while the thought streams, the row shows its status or "Thinking" with the shimmer. Reasoning without text and without a status gets no row in the group.

The task list (update_todos) shows above the message box. In the chat an update_todos call is a plain row without a chevron; it does not open, only a failed call opens to show its error. The same holds for an ask_user row: the questions themselves show in the form above the message box, so the row does not open. Its head has a progress ring and done/total, and the current item when collapsed. While items are open, the composer strip shows a checklist icon with the number of open items left of the context ring; clicking it folds the whole task card away and clicking again brings it back (tooltip "Hide task list (2 open)" / "Aufgabenliste ausblenden (2 offen)", "Show task list" / "Aufgabenliste einblenden"). The choice holds per chat while the app runs, and a new list after the last one ended shows again. In the list, open items have a dashed circle, the running item has a spinner on a highlighted pill, and done items a check. The list hides with a short exit motion once every item is done or the list is cleared. A list the agent left open when its turn ended stays visible but static (no spinner, no shimmer) until a later update_todos changes it. The next main-chat turn hands the open items back to the agent, which then continues or clears them; that note goes to the agent only and does not show in the chat.

## Computer use

With a model that takes images (vision in the model catalog), the main agent can see the Windows desktop through screenshots and control it with the real mouse and keyboard, to do things in other apps. Its tools are computer_screenshot, computer_click, computer_move, computer_drag, computer_scroll, computer_type, computer_key and computer_wait; sub-agents, workflow agents and plan mode do not get them. The built-in skill `computer-use` tells the agent how to work with them. Only one chat can control the computer at a time: while one chat holds it, a computer action of another chat is refused.

- Approval: in Ask and Auto the first computer action of a chat shows a card "May I control your computer?" ("Darf ich deinen Computer steuern?") that names the display and its size and says that screenshots of the screen are sent to the model provider while the agent works. The automatic review never decides it. "Yes, allow it in this chat until VantheaX quits" ("Ja, in diesem Chat erlauben, bis VantheaX beendet wird") lets that chat control the computer for the rest of the app session without another card; the permission is not saved, and other chats still ask. "No, tell it what to do differently" refuses. In Full it runs without a card.
- While a chat controls the computer, its running turn shows "Controlling your computer" ("Steuert deinen Computer") with a Stop button ("Stoppen"), and a small always-on-top indicator with Stop shows on the screen, also when VantheaX is in the background or in the tray. The indicator is hidden from the screenshots. Stop in the message box ends it too, and Ctrl+Alt+Esc (Strg+Alt+Esc) stops it from anywhere; when another program already owns that shortcut, only the Stop buttons work.
- Each action is one row: "Took a screenshot" ("Screenshot gemacht"), "Clicked 412, 230" ("412, 230 geklickt", also double, triple and right clicks), "Moved the pointer to 412, 230", "Dragged from 10, 20 to 300, 400", "Scrolled down", "Typed "hello"" (multi-line text reads "Typed text"), "Pressed ctrl+s" and "Waited 2s". A screenshot row opens to the screenshot; a click, move, drag or scroll row opens to the screenshot it acted on with the point marked, a drag with both ends joined by a dashed line. Clicking the image opens it large. Typing, key and wait rows do not open. In a tool group they count as "3 computer actions" ("3 Computeraktionen"). Screenshots are stored with the chat's other tool images.
- Coordinates are pixels of the latest screenshot. VantheaX scales screenshots to a size the model handles well and maps the points back to the real screen, display scaling included.
- The agent cannot reach UAC prompts, the lock and sign-in screen and other dialogs on the secure desktop, or windows of programs running as administrator.

## Inline visualizations

The main agent, also in plan mode, has the tool visualize; sub-agents (explore and worker) do not. It writes an HTML fragment with SVG, canvas and plain JavaScript, and the chat shows it inline in the answer at the point of the call: a chart, a diagram, a step-by-step walkthrough, a small calculator or simulator, a checklist or a table. It has no frame of its own and a transparent background, uses the app's fonts and colors, and grows with its content up to 8000 px tall. It is meant for explaining and showing; a website, app or page the user asks for is written as files into the project, not shown with visualize. The "/" command Visualize asks for a visualized answer to the next message.

While the model writes the call and while it runs, it is a tool row "Creating visualization: <title>" ("Erstellt Visualisierung: <title>") with a pie chart icon and nothing to open. When it is done, the visualization replaces the row and stays visible when the turn folds. A failed call stays a row ("Created visualization" / "Visualisierung erstellt") that opens to show its error, and a group of them reads "Created 2 visualizations" ("2 Visualisierungen erstellt").

The visualization runs in a sandboxed frame: no network (no requests, remote images, fonts, scripts or libraries), no localStorage, sessionStorage or cookies, no pop-ups, dialogs, forms, downloads or navigation, no permissions such as clipboard or notifications, and no access to the app, its settings or the project files. When its script throws, a muted line under it reads "Script error in this visualization: <message>" ("Skriptfehler in dieser Visualisierung: <message>"). The code is stored in the chat, so the visualization shows again when the chat is opened later; the model sees its own code in later rounds and gets back only a note that the visualization is shown.

The main agent, also in plan mode, has the tool show_images; sub-agents do not. It shows up to 10 image files from disk in the chat (PNG, JPEG, GIF, WebP or BMP, up to 20 MB each), project-relative or absolute, from any folder: screenshots, charts or exported figures the agent made, or images the user asked it to find. When the call is done, only the images appear in the answer at the point of the call, without a tool row, caption or path, at most 320 px high and side by side when there are several. While it runs, it is a tool row "Showing <file name>" ("Zeigt <file name>"), with "+N" when there are more. A click on an image opens it large; hovering an image shows "Open in Explorer" ("Im Explorer öffnen") at its top right, which opens Explorer with the file selected. The app keeps a copy of each image with the chat, so it stays visible when the original changes or is deleted, and the copy is removed once no chat shows it. The agent itself does not see the images; it uses view_image for that.

With image generation on (Settings > Image generation), the main agent has generate_image and present_images; sub-agents and plan mode do not. generate_image creates or edits an image with the chosen image model and saves it, but does not show it in the chat. Besides images the user asks for, the agent also generates image assets the requested work needs, such as a realistic background, a texture or a sprite, unless the user said not to, and copies the saved file from the path in the result into the project. The generation itself is a tool row in the tool group, "Generating image" ("Erzeugt Bild") and then "Generated image" ("Bild erzeugt"), without the prompt and without the picture, and it does not open. The agent decides where the images appear: present_images shows up to 10 generated images by id at the point of the call, usually once at the end with every image the user should see, as a grid without a tool row, caption or prompt; while it runs it is a row "Showing images" ("Zeigt Bilder"). A click on an image opens it large. Every generated image, also one the agent did not show, is listed in "Generated images" ("Generierte Bilder") in the More menu. In older chats the images generate_image made stay where they were, without the prompt.

## Background tasks

The main agent starts long non-interactive commands with `start_background_task` (name, command, optional project-relative cwd, optional shell: `powershell`, the default, or `bash` for Git Bash) and gets a task id at once. `get_background_task` reads status, exit code and the output; output over the 25000-token cap per tool result keeps its start and end, with a line saying how many characters are omitted and that redirecting the output to a file or filtering it shows them. `cancel_background_task` stops the task and its child processes. At most 16 background tasks run at once. The output survives an app restart. When a task ends and its result was not already read, the agent gets an event with the last 6000 characters of the output that says how many characters before them are omitted. While a turn runs in the chat, the event goes into that turn before its next model call; otherwise it starts a new turn. The chat shows nothing for the event, only the agent's reply to it, and the event tells the agent that the user does not see it. A task counts as ended when its shell exits. If a process the command started in the background (for example `cmd &` in Git Bash or Start-Process -NoNewWindow) keeps running and holds the output open, the task ends about two seconds after the shell exited anyway; output that process writes later is still added to the task. The task keeps its shell. The task's card in the chat shows the shell name (PowerShell or Git Bash) as its header.

While run_command or run_bash runs in the main chat (not in a sub-agent's transcript), the expanded command card shows "Put into background" ("In den Hintergrund verschieben") at the bottom right. Clicking it hands the running process (PowerShell or Git Bash), with its output so far, to the background task manager without restarting it. The call ends at once and tells the agent the task id, and the task no longer has the command's timeout. It appears in the Background Tasks panel and reports when it ends, like a task from start_background_task. The row then reads "Moved <command> to the background" and opens the task's live status and output. If 16 tasks are already running, the command stays in the foreground and the card says so. A command that is still running after 90 s moves to the background the same way by itself, and the agent is told the app moved it; the agent can keep a command in the foreground with the run_command or run_bash argument auto_background set to false. Sub-agent commands never move. A turn's Stop does not stop a moved command; cancel it in the panel or with cancel_background_task. A running command row in the main chat does not open by itself; open it to see the card and the button.

## Git Bash

When Git for Windows is installed, the agent also gets `run_bash` (main, plan and sub-agent workers). At startup the app looks for it in this order: the GitForWindows InstallPath registry value (HKLM, then HKCU), git.exe on PATH, then the standard install folders. It uses `<Git>\bin\bash.exe -c`, never the WSL bash.exe. If Git Bash is not found, the tool is not offered. The Files panel's Git view runs `<Git>\cmd\git.exe` from the same search, or else the first git.exe in an absolute PATH folder, always by its absolute path and never from the project folder.

A command runs non-interactive in the project folder or the given cwd, with stdout and stderr combined and the same timeout as run_command. Windows programs called from bash print UTF-8. Windows paths are written /c/Users/... or C:/Users/...; slash switches of Windows programs are doubled (cmd //c). A bash killed by a signal reports exit code 128+N and a line such as "[the shell was terminated by SIGTERM]".

Permissions are the same as for run_command, read as POSIX shell: hard blocks, the automatic review (its input names the shell), plan-mode read-only rules, Ask cards and prefix grants. The card is labelled "Git Bash", the row has its own $ icon, and "Put into background" works the same way. PowerShell stays the default shell; bash is meant for shell scripts, POSIX tools and pipelines the user asks for. When the user's custom instructions, a message or the project's instruction files ask for Git Bash, the agent runs every command bash can run through run_bash and keeps PowerShell only for cmdlets, the registry, services and Windows settings.

## Reasoning row

While the model streams reasoning text, the collapsed reasoning row shows a one or two sentence status of what the reasoning works on right now instead of "Thinking" ("Denkt nach"). The `side.reasoning_status` model of the catalog writes it, with reasoning effort minimal and no output cap, in the interface language from Settings > General. Its input is the user's last one to three messages and steers of the chat, the sub-agent's task in a sub-agent transcript, the status shown right now, and the last 1500 characters of the reasoning. A status is requested 2 seconds after the first visible reasoning text of a phase and again when the text first reaches 200 characters, when a new bold heading completes, or after 10 seconds with at least 1200 new characters. A newer request cancels the older one, and a retry ends the phase until the next attempt streams its own text. When a phase ends before it has a status and its reasoning text has at least 40 characters, one closing request with the end of the text is sent; a first request that is still running when the phase ends is allowed to finish. A status that arrives after its phase ended goes to that phase's reasoning block, and nothing arrives after the turn has ended. When the block ends, the row keeps a description of the thought: its status, else the last markdown heading or standalone bold line of the reasoning (at most about 120 characters); a thought without a description shows "Thought" ("Nachgedacht"). Reasoning between tool calls shows as a thought row inside the tool group (see Tool rows and the task list). Providers that hide their reasoning (encrypted or no reasoning text) get no status call: the chat shows the plain "Thinking" label without a chevron, and nothing can be expanded. A block whose reasoning text stays blank is removed when it ends. If the side call fails, the row keeps "Thinking". It works in the main chat and in sub-agent transcripts.
