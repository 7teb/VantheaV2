# VantheaX app reference

## Composer pickers

The model, the effort and the permission mode are app-wide settings chosen at the composer. They apply to new turns in every chat, including turns started by agent reports and background tasks.

- Model picker ("Select model" / "Modell wählen"): lists the agent models of the catalog with an "Effort" ("Aufwand") section for the chosen model.
- Mode picker ("Command permission" / "Befehlsfreigabe"): Ask (Fragen), Auto (Auto), Full auto (Voll-Auto).
- "Plan" chip: always in the composer bar, highlighted while plan mode is on; a click switches plan mode on or off. The + menu switch "Plan mode" and the "/" command Plan mode change the same setting. The agent may only read and inspect, then presents its plan with present_plan; accepting the plan starts a turn that implements it.

## Composer menus

The + button at the bottom left ("Add files and more" / "Dateien und mehr hinzufügen") opens a menu above the composer.
- The section "Add" ("Hinzufügen") holds three rows. "Files" ("Dateien") opens the file picker. "Work in a project" ("In einem Projekt arbeiten") opens the project choice: it picks a project folder and starts a new chat there, text typed in a new chat moves along, and its hint shows the current project or "No project" ("Kein Projekt"). "Plan mode" ("Planmodus") is a switch.
- Below that are the tabs "Skills" and "MCP". Skills lists the enabled skills that load without error, with their descriptions; MCP lists every configured server with its state. Clicking a skill or a ready MCP server adds a chip to the message, and clicking it again removes it. Servers that are not ready are shown disabled with their state. "Manage skills" ("Skills verwalten") and "Manage MCP servers" ("MCP-Server verwalten") open the settings.
- A chip shows above the text and can be removed with its x. When the message is sent, each chip becomes an instruction at the top of the message: Use the skill "<name>" for this request: load it with read_skill first and follow it. / Use the tools of the MCP server "<name>" for this request. A message with only chips can be sent.

Typing "/" at the start of the message or after a space opens "Commands" ("Befehle"). The list filters as you type, and the English command names also match in the German interface. Arrow keys move, Enter or Tab runs a command, Esc closes the list until the "/word" is gone, Backspace on an empty filter removes the "/" and closes it, ArrowRight opens a submenu and ArrowLeft or Backspace goes back. Running a command removes the "/word" from the draft. When nothing matches, no list shows and Enter sends the text.
- Compact ("Komprimieren"): compacts now, the same as "Compact now" in the context popup; its hint shows how full the context is.
- Auto-compact ("Auto-Komprimierung"): submenu 50 to 95% for the current model (see context.md).
- Context limit ("Kontextlimit"): submenu with "Model maximum" and presets below the window (see context.md).
- Archive chat / Restore chat ("Chat archivieren" / "Chat wiederherstellen"): archiving the open chat moves to a new chat (see Chat archive).
- Pin chat / Unpin chat ("Chat anpinnen" / "Chat lösen").
- Fork chat ("Chat verzweigen"): copies the chat up to its latest message into a new chat and opens it.
- Memories ("Erinnerungen"): a panel above the composer with the saved memories, a delete button per entry and a field to add one (see the Memory settings).
- Initialize ("Initialisieren"): starts a turn that shows in the chat as your message "/init" and asks the agent to inspect the project and create AGENTS.md, or update it if it exists (see Initialize). In a new chat of a project it first creates the chat, moves the typed text along and starts the request there.
- Plan mode ("Planmodus"): switch.

A row that cannot run is disabled and shows the reason. "Needs a chat" ("Braucht einen Chat") applies to Compact, Archive, Pin and Fork. "Needs a project" ("Braucht ein Projekt") applies to Initialize in a chat or new chat without a project. "Turn running" ("Turn läuft") applies to Compact, Fork, Initialize and archiving. "Compacting" ("Wird komprimiert") applies to Compact and Initialize while a compaction runs. "No model selected" ("Kein Modell gewählt") applies to Auto-compact and Context limit. Pin and Unpin are disabled on an archived chat with "Restore the chat first" ("Erst den Chat wiederherstellen").

While the + menu or the command list is open, the task list and the other cards above the composer slide up above it and back when it closes. When the room above the composer is too small, the menu gets shorter and the cards get one shared height limit and scroll on their own, so the stack stays inside the window.

## Queued messages

The composer, the message editor and the feedback field of approval and question cards check spelling in German and English and underline misspelled words in red; a right click on one offers suggestions and "Add to dictionary" ("Zum Wörterbuch hinzufügen"). Other fields (settings, search, rename) do not check spelling.

A message sent with Enter (or the send button) while a turn runs does not go to the agent at once: it waits as a row in a panel that comes out of the top edge of the composer and is sent when the turn ends. "Steer" ("Steuern") on the row hands it to the running turn, which adds it at its next model round. Each row has "Steer" ("Steuern") while a turn runs or "Send" ("Senden") when none runs, a trash button ("Discard" / "Verwerfen") and a "..." menu with "Edit message" ("Nachricht bearbeiten"). Edit message takes the message out of the queue and puts its text and attachments back into the composer in front of anything already typed there. A row marked "Waiting for next round" ("Wartet auf nächste Runde") is already handed to the turn and cannot be edited or discarded; a row with a warning icon was not sent and can be steered, sent, edited or discarded again.

## File changes and Undo

A finished turn that changed files with write_file or replace_in_file ends with a file card listing those files with their +/- line counts. Clicking a file in the card opens it in the Files panel with its current content. Only the card of the newest assistant turn has an "Undo" ("Rückgängig machen") button; it is disabled while a turn runs. Undo does not restore files itself: it sends a message to the agent that names the files of that turn (marking the ones it created) and asks it to put edited files back, delete created ones, undo changes it made through commands and change nothing else. The message shows in the chat as the chip "Undo requested" ("Rückgängig machen angefordert"), uses the current model, effort and permission mode, and counts as the user's own request for the automatic review. The agent rebuilds earlier content from its own edits or from git, so a file it overwrote without reading first may not come back exactly; it is asked to say so.

## Initialize

The "/" command Initialize sends the agent a request to inspect the open project and create AGENTS.md in the project root, or update it if it exists: install, build, run and test commands (including a single test), lint and format, the layout, the conventions the code follows, and gotchas, only what it verified, keeping the rules a person wrote and changing no other file. The request shows in the chat as a normal user message "/init" (it can be copied and forked, not edited), while the agent receives the full request text; it uses the current model, effort and permission mode, and counts as the user's own request for the automatic review. Writing AGENTS.md still asks for approval in Auto, like every change to AGENTS.md or CLAUDE.md.

## Permission modes

The setting values are `ask`, `auto` and `full`; the UI labels are Ask ("Approve every command" / "Jeden Befehl bestätigen"), Auto ("Safe commands run, risky ask" / "Sichere laufen, riskante fragen") and Full auto ("Runs every command, including dangerous ones" / "Führt jeden Befehl aus, auch gefährliche").

- Ask: every command and every file write waits for the user's approval, except commands covered by an earlier "don't ask again for commands starting with" approval in the same chat, and the screenshots check_page saves into the page's `_shots` folder. Adding an MCP server, installing a skill, and saving or deleting a memory always ask. read_file, grep_files, list_files, get_file_outline and view_image ask with a card when their path names a secret file or folder (.env files, keys, credential files, .ssh, .git/config, .git/hooks).
- Auto: file writes inside the project run directly, except changes to AGENTS.md and CLAUDE.md, which ask. Every command, read-only ones included, is reviewed by a separate overseer model (the `side.overseer` model of the catalog) against the user's messages, custom instructions, the project instruction files and the earlier decisions of the chat; it runs if allowed, asks if the review wants the user's approval, and is refused with the reason if it breaks a rule. Parts of a command the app could not read go to the review as information; the review's verdict decides. A script that contains a hard-blocked operation asks until that exact version was approved. Reading the content of .env files, API keys, tokens, private keys or credential files is denied by the review, whether by command or by a file tool that names the secret path, unless a user message, the custom instructions or an earlier approval of that read explicitly allows it. The denial tells the agent to ask in chat, and after the user's yes the next attempt is allowed. A folder-wide grep_files skips the content of secret files. A folder-wide list_files shows secret file names but leaves out the files inside secret folders such as .ssh. Adding an MCP server, installing a skill, and saving or deleting a memory pass the automatic review first; allowed calls run, the rest ask or are refused.
- Full: commands, file writes and MCP tools run without asking, except dangerous tools of untrusted MCP servers. Adding an MCP server, installing a skill, and saving or deleting a memory pass the automatic review first; allowed calls run, the rest ask or are refused. Commands are not reviewed in Full, so a command that reads a .env file or a key runs without being stopped. When a file tool names a secret path, the review still decides.
- In every mode, Ask included, texts that agents pass to sub-agents (message_peer and message_agent texts, and the tasks of deploy_agent and continue_agent) go through the automatic review before they arrive. They show a card only when the review asks for the user's approval or is unavailable; a denied text never arrives. Details are in agents.md.
- In every mode some catastrophic commands are hard-blocked and cannot be approved: diskpart, bcdedit, disk-wiping cmdlets (Clear-Disk, Format-Volume, Initialize-Disk, Reset-PhysicalDisk), formatting a drive, deleting volume shadow copies, cipher /w, deleting Windows, System32, Program Files, boot files or a drive root, and deleting HKEY_LOCAL_MACHINE registry keys. The same blocks apply to Git Bash commands in their bash spellings (for example rm -rf on those folders through /c/... or C:/... paths, find -delete, xargs rm, dd to a disk device). A target built from variables or command output is blocked when its visible part already names one of these places, and goes to the review otherwise.
- A denial is returned to the agent with the user's reason. Approving a command can offer "Yes, and don't ask again for commands starting with: <prefix>", which applies to that chat. The prefix applies only to the shell it was given in (PowerShell or Git Bash).
- A card that carries a review note (the review asked for the user's approval, or the review was unavailable) skips itself after 15 seconds without an answer: the Skip button fills up as a countdown, the step ends as "Skipped, no answer within 15 s" ("Übersprungen, keine Antwort in 15 s") and the agent gets a result saying nobody answered, not that the user denied it. Typing into the feedback field stops the countdown for that card. Cards without a review note (Ask mode, AGENTS.md and CLAUDE.md edits in Auto) wait for the user without a time limit.
- When the safety review is unavailable, a command or MCP approval can offer "Yes, and allow everything in this chat and its agents for 10 minutes". That window acts like Full for commands, file writes and read-only or state-changing MCP tools of that chat and its agents.

## Efforts

Each catalog model lists its own efforts, ordered from lowest to highest, out of: none, minimal, low, medium, high, xhigh, max. The UI labels are Off (Aus), Minimal (Minimal), Low (Niedrig), Medium (Mittel), High (Hoch), Extra high (Sehr hoch), Max (Max). Every model that has efforts also gets Major (Major).

Major is not a provider setting: the request uses the model's highest real effort. In addition, outside plan mode the main agent gets instructions to deploy independent parts to sub-agents in parallel and to run an independent review agent before it finishes non-trivial work, and while agents of the chat run, the turn waits up to 30 minutes for an agent update, a report or a user message before it ends (see agents.md).

## Titlebar

From left to right on the right side: the panel buttons Terminal, Browser and Files (Dateien), then the More menu ("More" / "Mehr", three dots), then the window controls. Each panel button opens or closes its panel. A yellow dot on the More button means a sub-agent of this chat waits for approval.

- Terminal: PowerShell terminals of the current chat. Each chat has its own terminal tabs ("New terminal" / "Neues Terminal" adds one). Opening the panel starts a terminal for the current chat when it has none. Switching to another chat while the panel is open starts nothing: a chat without a terminal shows a "New terminal" ("Neues Terminal") button, and only a click on it or on the + starts one. Terminals start in the chat's project folder, or in its workspace folder for a chat without a project; a new chat without a project starts in the home folder. Switching chats shows that chat's terminals and keeps the others running in the background. Terminals opened on the new-chat screen move into the chat that its first message creates. Deleting a chat closes its terminals; quitting the app closes all of them. The agent's own commands (run_command, run_bash) run separately and never use this panel.
- Browser: the in-app browser the agent can drive. Tabs belong to one chat: the agent of a chat lists, opens, drives and closes only that chat's tabs, and other chats cannot see them. The agent browses in the background, so the panel does not open and focus does not move while it works; opening the Browser panel shows the current chat's tabs live, including the ones the agent drives, and you can click and type in them. Closing the panel or switching chats does not stop or reload any page; a chat keeps its tabs until you close them or delete the chat, and quitting closes all of them. Tabs opened on the new-chat screen move to the chat created from it and keep their logins. Every chat has its own browser profile: logins, cookies and site data stay in that chat, other chats never see them, nothing is written to disk, and the profile is cleared when the chat's last tab closes, when the chat is deleted and when the app quits. A tab the agent drives in the background renders at 1280 by 800; while it is shown in the panel it takes the panel's size and goes back to 1280 by 800 when the panel closes or shows another tab. Page dialogs are answered by the app: alert is dismissed, confirm and prompt are cancelled, also while the tab is shown in the panel, and the agent's next browser result names each dialog with its text. When a page asks before you leave it, a background tab leaves without asking; a tab shown in the panel asks you whether to leave or stay.
  The agent reads a tab's console with browser_console (console messages, uncaught exceptions and failed requests of the current page; numbered entries, after=<last_seq> returns only newer ones; the log restarts on navigation and keeps the newest 1000 entries) and inspects page state with browser_eval, which runs only side-effect-free JavaScript (V8 refuses anything that could change the page) with a 10 second limit. Both work in plan mode and need no approval.
- Files (Dateien): the folder of the current chat. That is its project folder, or for a chat without a project its own workspace folder; a new chat without a project shows "Open a project to browse its files" ("Öffne ein Projekt, um seine Dateien zu sehen"). On the left, a file tree loads each folder when it is opened. It hides the same folders as list_files (.git, node_modules, dist, build, bin, obj, target and similar), and a folder with more than 2000 entries shows the first 2000 plus "N more not shown" ("N weitere nicht angezeigt"). The field "Filter files" ("Dateien filtern") lists files whose name contains the text, at most 300, including files inside folders such as .ssh, which the tree also shows. On the right, a read-only viewer has a tab per open file, line numbers, syntax highlighting up to 200,000 characters, the file's path, line count and size, "Copy path" ("Pfad kopieren") and "Show in Explorer" ("Im Explorer zeigen"). A file over 1 MB shows its first 1 MB with a note, and a binary file shows a note instead of content. Secret files such as .env are listed and shown like any other file: the panel is for the user and sends nothing to a model. While the panel is open it watches the folder and updates the tree and open files when files change on disk. The header buttons hide or show the tree ("Hide file tree" / "Dateibaum ausblenden", only while a file is open), widen the panel to its maximum width ("Expand panel" / "Panel vergrößern", again to "Restore panel width" / "Panelbreite zurücksetzen") and close it. Each chat keeps its own Files panel state: open file tabs, expanded folders and the filter. Switching chats shows that chat's state and refreshes it from disk, and a chat created from the new-chat screen keeps what was opened there.

More menu:

- "Background tasks" ("Hintergrund-Tasks"): opens the Background Tasks panel of the current chat. It lists the chat's sub-agents and its background shell tasks together, newest first, in two sections with a chevron each: "Running" ("Läuft") and "Ran" ("Beendet"). Collapsing a section is remembered. An agent row shows its topic, profile (and the tools removed from it, if any) and model, a stop button while it runs, and its runs; opening a run shows its transcript, its report and a Stop button while it runs, and "Back to background tasks" ("Zurück zu Background Tasks") returns to the list. A shell task shows its command, shell, status, duration, exit code, a collapsible output and a cancel button while it runs. The trash button "Clear finished commands" ("Beendete Befehle entfernen") removes finished shell tasks; agents stay listed. A badge shows how many agent runs and tasks of the chat are running, and a yellow dot on the item means an agent waits for approval. Opening an agent from the chat (its tool row or "Open transcript" ("Transcript öffnen")) opens this panel on that transcript.
- "Generated images" ("Generierte Bilder"): the generated images of the project, with pin, rename and export.
- "Keep computer awake" ("Computer wach halten"), with the note "Only for this session" ("Nur für diese Sitzung"): a toggle that starts Electron's `prevent-app-suspension` power save blocker, which keeps the system from entering a low-power mode. It is not saved and is switched off when the app quits. The screen can still turn off; only system sleep is prevented.

## Chat archive

Archive ("Archivieren") in a chat's "..." menu in the sidebar archives the chat; it is disabled while the chat's turn runs. The "/" command Archive chat does the same for the open chat. An archived chat leaves the Pinned, project and No project lists of the sidebar and the previous/next chat shortcuts. Archiving the open chat switches to a new chat in the same project. While at least one chat is archived, "Archived" ("Archiviert") with the count sits above Settings at the bottom of the sidebar. It opens "Archived chats" ("Archivierte Chats"), newest first. Clicking a row opens the chat; an archived chat can be read like any other; any turn that starts in it (a message, Continue, Initialize, an accepted plan, Undo, Compact or a report from one of its agents) restores it to the lists, pin included. "Restore" ("Wiederherstellen") puts the chat back into the lists, pin included, and the trash button deletes it after a confirmation. Search finds archived chats and marks them with an archive icon and an "Archived" ("Archiviert") tag; the Recent list shown before typing leaves them out. A fork of an archived chat is not archived. Chats saved before the archive existed load as not archived.

## Tool rows and the task list

Each tool call is one row with an icon and a label. A row adds a short status only when it shows that status nowhere else:
- a search with no hits ("No matches" / "Keine Treffer"), or a capped or incomplete search;
- an MCP error;
- a peer message that was not delivered ("Not running" / "Läuft nicht", "Already sent" / "Schon gesendet");
- the live status of a background task or agent run, in the interface language (a task or run that is no longer in the list, for example after "Clear finished commands" / "Beendete Befehle entfernen", keeps its final status or shows "Ended" / "Beendet");
- the date and time from datetime.

Only command rows (run_command and run_bash) show a duration: a live counter while the command runs, the final time when it ended. Rows of the running turn fade in, the icon of a running row is brighter, child rows inside a tool group are dimmer than the group head, and running items use a circle spinner. A failed or timed out command row can be opened to show its card with the exit code. The running command card shows "Running" ("Läuft") at the bottom right until it ends. Reads and skills use an open book, MCP a plug, memory a worm and tool groups a terminal square. Sub-agents have no robot icon: each agent shows a small colored pixel critter picked from its name (the same name always gets the same critter) on its tool rows (deploy, continue, status, stop, messages), on its report rows, on "View transcript" and in the agents panel, and the critter hops slightly while that agent runs. Agent rows without one specific agent (list_agents, a message to the main agent) show a neutral critter in the row color.

The task list (update_todos) shows above the message box. Its head has a progress ring and done/total, and the current item when collapsed. The list hides with a short exit motion once every item is done or the list is cleared. A list the agent left open when its turn ended stays visible but static (no spinner, no shimmer) until a later update_todos changes it. The next main-chat turn starts with an "Open todos carried over" ("Offene To-dos übernommen") notice that hands the open items back to the agent, which then continues or clears them.

## Background tasks

The main agent starts long non-interactive commands with `start_background_task` (name, command, optional project-relative cwd, optional shell: `powershell`, the default, or `bash` for Git Bash) and gets a task id at once. `get_background_task` reads status, exit code and the output; output over the 25000-token cap per tool result keeps its start and end, with a line saying how many characters are omitted and that redirecting the output to a file or filtering it shows them. `cancel_background_task` stops the task and its child processes. At most 16 background tasks run at once. The output survives an app restart. When a task ends and its result was not already read, a "Background task finished" ("Hintergrundaufgabe beendet") event starts a new turn in the chat once no turn is running; the event shows the last 6000 characters of the output and says how many characters before them are omitted. A task counts as ended when its shell exits. If a process the command started in the background (for example `cmd &` in Git Bash or Start-Process -NoNewWindow) keeps running and holds the output open, the task ends about two seconds after the shell exited anyway; output that process writes later is still added to the task. The task keeps its shell. In the Background Tasks panel the status line of a task starts with the shell name (PowerShell or Git Bash), and the task's card in the chat shows it as its header.

While run_command or run_bash runs in the main chat (not in a sub-agent's transcript), the expanded command card shows "Put into background" ("In den Hintergrund verschieben") at the bottom right. Clicking it hands the running process (PowerShell or Git Bash), with its output so far, to the background task manager without restarting it. The call ends at once and tells the agent the task id, and the task no longer has the command's timeout. It appears in the Background Tasks panel and reports when it ends, like a task from start_background_task. The row then reads "Moved <command> to the background" and opens the task's live status and output. If 16 tasks are already running, the command stays in the foreground and the card says so. A turn's Stop does not stop a moved command; cancel it in the panel or with cancel_background_task. A running command row in the main chat does not open by itself; open it to see the card and the button.

## Git Bash

When Git for Windows is installed, the agent also gets `run_bash` (main, plan and sub-agent workers). At startup the app looks for it in this order: the GitForWindows InstallPath registry value (HKLM, then HKCU), git.exe on PATH, then the standard install folders. It uses `<Git>\bin\bash.exe -c`, never the WSL bash.exe. If Git Bash is not found, the tool is not offered.

A command runs non-interactive in the project folder or the given cwd, with stdout and stderr combined and the same timeout as run_command. Windows programs called from bash print UTF-8. Windows paths are written /c/Users/... or C:/Users/...; slash switches of Windows programs are doubled (cmd //c). A bash killed by a signal reports exit code 128+N and a line such as "[the shell was terminated by SIGTERM]".

Permissions are the same as for run_command, read as POSIX shell: hard blocks, the automatic review (its input names the shell), plan-mode read-only rules, Ask cards and prefix grants. The card is labelled "Git Bash", the row has its own $ icon, and "Put into background" works the same way. PowerShell stays the default shell; bash is meant for shell scripts, POSIX tools and pipelines the user asks for.

## Reasoning row

While the model streams reasoning text, the collapsed reasoning row shows a one or two sentence status of what the reasoning works on right now instead of "Thinking" ("Denkt nach"). The `side.reasoning_status` model of the catalog writes it, with reasoning effort minimal and no output cap, in the interface language from Settings > General. Its input is the user's last one to three messages and steers of the chat, the sub-agent's task in a sub-agent transcript, the status shown right now, and the last 1500 characters of the reasoning. A status is requested 2 seconds after the first visible reasoning text of a phase and again when the text first reaches 200 characters, when a new bold heading completes, or after 10 seconds with at least 1200 new characters. A newer request cancels the older one, and a retry ends the phase until the next attempt streams its own text. When the block ends the row shows "Thought for Xs" ("Xs nachgedacht"). Providers that hide their reasoning (encrypted or no reasoning text) get no status call: the chat shows the plain "Thinking" label without a chevron, and nothing can be expanded. A block whose reasoning text stays blank is removed when it ends. If the side call fails, the row keeps "Thinking". It works in the main chat and in sub-agent transcripts.

## Settings

Sections: App group with General (Allgemein: Language, OpenRouter API key, Key balance) and Personalization (Personalisierung: Personality, Custom instructions, Memory); Integrations group (Integrationen) with Web search (Websuche, Tavily API key), Image generation (Bildgenerierung), MCP servers (MCP-Server) and Skills (see skills.md).

Web search: a search returns the matching sources with the relevant excerpts of their text, or at Advanced depth a research answer with source links; results carry their publish date when Tavily knows it, and the agent can ask for news and a time range per search. Reading specific URLs always returns the page text itself to the agent, in windows that fit one tool result with an offset to read on; the depth setting only chooses Tavily's basic or advanced extraction there. URLs that fail are named in the result and shown in red under the sources.

Memory ("Memory (experimental)" / "Erinnerung (experimentell)"): with "Enable memories" ("Erinnerungen aktivieren") on, the `side.memory` model reads the user's message and the steers typed during that turn after every finished main turn (done, stopped, failed or blocked), unless "Skip tool-assisted chats" ("Toolgestützte Chats nicht berücksichtigen") is on and the turn used a tool. Editing a user message scans the edited text again. Candidates that are explicit, quoted from those words, free of secrets and at confidence 0.85 or higher are saved directly under "Saved memories" ("Gespeicherte Erinnerungen"), where "Remove memory" ("Erinnerung entfernen") deletes one. A candidate that matches a fact the user discarded before is held under "Memory review" ("Erinnerungen prüfen") with Keep ("Behalten") and Discard ("Verwerfen"). Candidates still waiting for review at startup are saved by the same rule. The "/" command Memories opens a small panel above the composer ("Memories" / "Erinnerungen") with the saved memories, a trash button per entry and a field to add one; a memory added there is saved directly as a global memory (no review), up to 25000 characters, secrets redacted, and adding the exact same text again keeps a single entry. Escape or the close button closes it. While "Enable memories" is off, the panel notes that saved memories are not used.

The project root may contain AGENTS.md or CLAUDE.md (checked in that order, first non-empty file wins, cut at 24000 characters). It is loaded into the system prompt as project instructions.

## Where data lives

Everything is under `%APPDATA%\VantheaX\v2`:

- `settings.json`: settings (language, model, effort, mode, projects, personality, custom instructions, memory, web search, image generation, MCP servers, MCP tool overrides, disabled skills).
- `secrets.json`: the OpenRouter and Tavily keys, encrypted with Electron safeStorage.
- `chats\`: `index.json`, `data\` and `search\`.
- `media\attachments\` and `media\images\`: attached files and generated images; `artifacts.json` lists the artifacts.
- `background.json`: background tasks.
- `agents\<agent id>\`: agent context, run journals (`<run id>.jsonl`) and reports (`<run id>.report.md`).
- `memories.json`: memories, plus one scan record per scanned user message. Each record has the outcome (scanned, unparsable, skipped_tools, failed), the error of a failed side call, and how many candidates the memory model returned, saved, held for review or dropped, with the reason (kind, empty, not_explicit, secret, evidence_not_in_message, low_confidence, no_project).
- `skills\`: user skills and `installed.json`.
- `workspaces\<chat id>\`: working folder of a chat that has no project.

Files directly in `%APPDATA%\VantheaX` (outside `v2`) belong to the previous version; their settings, chats, memories, skills, artifacts and media are imported into `v2`, and the old files are left in place. An older `v2\snapshots\` folder from the previous Undo is deleted once at startup.

## Model catalog

The catalog is `config/models.json` inside the app (in the packaged app it is part of `resources\app.asar`, so changing it means rebuilding). It is the only place model ids are written down. It has three parts:

- `models`: the agent models. Each entry has `id` (OpenRouter id), `label`, `provider`, `provider_order`, `efforts`, `default_effort`, `vision`, `context_length`, `max_output`, optional `reasoning_passback`, optional `note` and optional `fallback` (another model id).
- `side`: fixed models for side jobs: `title`, `overseer`, `vision`, `web_answer`, `memory`, `reasoning_status`.
- `image_models`: models for generate_image, each with `id`, `label` and `quality`.

All model calls go through OpenRouter with the key from Settings > General.

When a model call hits a rate limit (HTTP 429), a provider outage, an interrupted stream or a timeout, the app retries it after 2, 5, 10, 20, 30, 60, 120 and 120 s, at most 9 attempts and never longer than 10 minutes after the first attempt; a Retry-After from the server is followed up to 120 s. The answer shows "Answer interrupted, attempt n/total" ("Antwort unterbrochen, Versuch n/total") meanwhile. A model with a fallback route switches to it after 3 failed attempts. Compaction calls use their own retry plan (see context.md).

## Built-in skills in the package

The built-in skills, including this one, ship as plain files in `resources\skills` next to VantheaX.exe, outside `app.asar`.
