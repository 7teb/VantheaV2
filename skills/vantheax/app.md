# VantheaX app reference

## Composer pickers

The model, the effort and the permission mode are app-wide settings chosen at the composer. They apply to new turns in every chat, including turns started by agent reports and background tasks.

- Model picker ("Select model" / "Modell wählen"): lists the agent models of the catalog with an "Effort" ("Aufwand") section for the chosen model.
- Mode picker ("Command permission" / "Befehlsfreigabe"): Ask (Fragen), Auto (Auto), Full auto (Voll-Auto).
- "Plan" chip: shows in the composer bar only while plan mode is on, highlighted like the other chips; hovering turns its icon into an x and a click switches plan mode off. The + menu switch "Plan mode" and the "/" command Plan mode change the same setting. The agent may only read and inspect, then presents its plan with present_plan; accepting the plan starts a turn that implements it.

## Composer menus

The + button at the bottom left ("Add files and more" / "Dateien und mehr hinzufügen") opens a menu above the composer.
- The section "Add" ("Hinzufügen") holds three rows. "Files" ("Dateien") opens the file picker. "Work in a project" ("In einem Projekt arbeiten") opens the project choice: it picks a project folder and starts a new chat there, text typed in a new chat moves along, and its hint shows the current project or "No project" ("Kein Projekt"). "Plan mode" ("Planmodus") is a switch.
- Below that are the tabs "Skills" and "MCP". Skills lists the enabled skills that load without error, with their descriptions; MCP lists every configured server with its state. Clicking a skill or a ready MCP server adds a chip to the message, and clicking it again removes it. Servers that are not ready are shown disabled with their state. "Manage skills" ("Skills verwalten") and "Manage MCP servers" ("MCP-Server verwalten") open the settings.
- A chip shows in the composer bar after the mode picker (and after the Plan chip while plan mode is on), highlighted like the Plan chip; hovering it turns its icon into an x, and a click removes it. When the message is sent, each chip becomes an instruction at the top of the message: Use the skill "<name>" for this request: load it with read_skill first and follow it. / Use the tools of the MCP server "<name>" for this request. The Visualize chip from the "/" command becomes: Answer this message with the visualize tool: build an interactive visualization that explains or shows the answer, and keep the text around it short. A message with only chips can be sent.

Typing "/" at the start of the message or after a space opens "Commands" ("Befehle"). The list filters as you type, and the English command names also match in the German interface. Arrow keys move, Enter or Tab runs a command, Esc closes the list until the "/word" is gone, Backspace on an empty filter removes the "/" and closes it, ArrowRight opens a submenu and ArrowLeft or Backspace goes back. Running a command removes the "/word" from the draft. When nothing matches, no list shows and Enter sends the text.
- Compact ("Komprimieren"): compacts now, the same as "Compact now" in the context popup; its hint shows how full the context is.
- Auto-compact ("Auto-Komprimierung"): submenu 50 to 95% for the current model (see context.md).
- Context limit ("Kontextlimit"): submenu with "Model maximum" and presets below the window (see context.md).
- Archive chat / Restore chat ("Chat archivieren" / "Chat wiederherstellen"): archiving the open chat moves to a new chat (see Chat archive).
- Pin chat / Unpin chat ("Chat anpinnen" / "Chat lösen").
- Fork chat ("Chat verzweigen"): copies the chat up to its latest message into a new chat and opens it.
- Memories ("Erinnerungen"): a panel above the composer with the saved memories, a delete button per entry and a field to add one (see the Memory settings).
- Initialize ("Initialisieren"): starts a turn that shows in the chat as your message "/init" and asks the agent to inspect the project and create AGENTS.md, or update it if it exists (see Initialize). In a new chat of a project it first creates the chat, moves the typed text along and starts the request there.
- Create GitHub repository ("GitHub-Repository erstellen", found by typing /gitinit, git or github): starts a turn that shows in the chat as your message "/gitinit". The agent first asks three questions in the question form (the repository name, private or public, and which GitHub users to invite) and creates nothing before you answer. Then it checks the GitHub CLI (gh auth status; without gh or its login it tells you to install it and run gh auth login yourself), stops to ask if a remote named origin already exists, runs git init and makes a first commit with a .gitignore that keeps out build output, dependencies, logs and secrets when the folder is not a repository yet, creates and pushes the repository with gh repo create, invites the named users (each gets a GitHub invitation to accept) and ends with the repository URL. Like Initialize it works in a new chat of a project and counts as your own request for the automatic review.
- Plan mode ("Planmodus"): switch.
- Visualize ("Visualisieren", also found by typing chart, diagram, graph, visual or widget): switch; it adds or removes a "Visualize" ("Visualisieren") chip with a pie chart icon in the composer bar, which asks the agent to answer the next message with an inline visualization (see Inline visualizations). It needs no chat and no project.

A row that cannot run is disabled and shows the reason. "Needs a chat" ("Braucht einen Chat") applies to Compact, Archive, Pin and Fork. "Needs a project" ("Braucht ein Projekt") applies to Initialize and Create GitHub repository in a chat or new chat without a project. "Turn running" ("Turn läuft") applies to Compact, Fork, Initialize, Create GitHub repository and archiving. "Compacting" ("Wird komprimiert") applies to Compact, Initialize and Create GitHub repository while a compaction runs. "No model selected" ("Kein Modell gewählt") applies to Auto-compact and Context limit. Pin and Unpin are disabled on an archived chat with "Restore the chat first" ("Erst den Chat wiederherstellen").

While the + menu or the command list is open, the task list and the other cards above the composer slide up above it and back when it closes. When the room above the composer is too small, the menu gets shorter and the cards get one shared height limit and scroll on their own, so the stack stays inside the window.

## Dictation

The microphone button left of the send button dictates into the message box. A click asks for the microphone (a spinner while it opens; clicking it then cancels) and starts recording: the button turns into a small pill with a scrolling waveform of the input level and a stop square. Clicking the pill stops and puts the transcript at the cursor of the message box, with a space on each side where words would touch, so it can be edited before sending. Enter or the send button while recording stops, transcribes and sends in one step. Esc cancels the recording without sending anything, as does switching to another chat. While the text is transcribed the button shows a spinner. The audio (WebM/Opus, recorded in the window) goes to OpenRouter's transcription endpoint with the catalog's `side.transcription` model (ElevenLabs Scribe v2, which keeps German and English apart in mixed speech); nothing is saved to disk. A recording shorter than a quarter second is dropped. Errors show under the message box: no microphone access ("Enable microphone access to dictate" / "Erlaube den Mikrofonzugriff, um zu diktieren"), no microphone, the microphone in use by another app, an empty result ("Didn't catch that, please try again"), or the provider error.

## Queued messages

The composer, the message editor and the feedback field of approval and question cards check spelling in German and English and underline misspelled words in red; a right click on one offers suggestions and "Add to dictionary" ("Zum Wörterbuch hinzufügen"). Other fields (settings, search, rename) do not check spelling.

A message sent with Enter (or the send button) while a turn runs does not go to the agent at once: it waits as a row in a panel that comes out of the top edge of the composer and is sent when the turn ends. "Steer" ("Steuern") on the row hands it to the running turn, which adds it at its next model round. In the chat the steered message then shows inside the running turn, where the turn picked it up, as the same right-aligned bubble as a normal user message, attachments included. Each row has "Steer" ("Steuern") while a turn runs or "Send" ("Senden") when none runs, a trash button ("Discard" / "Verwerfen") and a "..." menu with "Edit message" ("Nachricht bearbeiten"). Edit message takes the message out of the queue and puts its text and attachments back into the composer in front of anything already typed there. A row marked "Waiting for next round" ("Wartet auf nächste Runde") is already handed to the turn and cannot be edited or discarded; a row with a warning icon was not sent and can be steered, sent, edited or discarded again.

## File changes and Undo

A finished turn that changed files with write_file or replace_in_file ends with a file card listing those files with their +/- line counts. The card appears only when the turn really ends: not while it streams and not while a sub-agent it started still runs; for a turn joined by agent report turns it is one card at the very end for the files of all of them. Clicking a file in the card opens it in the Files panel with its current content. Only the card of the newest assistant turn has an "Undo" ("Rückgängig machen") button, and a joined card only when all its files come from that newest turn; it is disabled while a turn runs. Undo does not restore files itself: it sends a message to the agent that names the files of that turn (marking the ones it created) and asks it to put edited files back, delete created ones, undo changes it made through commands and change nothing else. The message shows in the chat as the chip "Undo requested" ("Rückgängig machen angefordert"), uses the current model, effort and permission mode, and counts as the user's own request for the automatic review. The agent rebuilds earlier content from its own edits or from git, so a file it overwrote without reading first may not come back exactly; it is asked to say so.

## Initialize

The "/" command Initialize sends the agent a request to inspect the open project and create AGENTS.md in the project root, or update it if it exists: install, build, run and test commands (including a single test), lint and format, the layout, the conventions the code follows, and gotchas, only what it verified, keeping the rules a person wrote and changing no other file. The request shows in the chat as a normal user message "/init" (it can be copied and forked, not edited), while the agent receives the full request text; it uses the current model, effort and permission mode, and counts as the user's own request for the automatic review. Writing AGENTS.md still asks for approval in Auto, like every change to AGENTS.md or CLAUDE.md.

## Permission modes

The setting values are `ask`, `auto` and `full`; the UI labels are Ask ("Approve every command" / "Jeden Befehl bestätigen"), Auto ("Safe commands run, risky ask" / "Sichere laufen, riskante fragen") and Full auto ("Runs every command, including dangerous ones" / "Führt jeden Befehl aus, auch gefährliche").

- Ask: every command and every file write waits for the user's approval, except commands covered by an earlier "don't ask again for commands starting with" approval in the same chat, and the screenshots check_page saves into the page's `_shots` folder. Adding an MCP server, installing a skill, and saving or deleting a memory always ask. read_file, grep_files, list_files, get_file_outline and view_image ask with a card when their path names a secret file or folder (.env files, keys, credential files, .ssh, .git/config, .git/hooks).
- Auto: file writes inside the project run directly, except changes to AGENTS.md and CLAUDE.md, which ask. Every command, read-only ones included, is reviewed by a separate overseer model (the `side.overseer` model of the catalog). The review judges the risk of the step, not whether the user asked for that exact step; it reads the user's messages, custom instructions, the project instruction files, the earlier decisions of the chat, the scripts the command runs and the target facts. Low and medium risk runs without a card: builds, tests and smoke tests, the project's scripts and scripts the agent wrote (also when they create or overwrite files in the project or a temporary folder), installing the project's dependencies, local git work, starting the program being built and stopping processes the agent started, and creating, overwriting or deleting files that were created or written in this chat (not an older file the agent only edited), that are missing or empty, or that are generated output. High risk that no user message clearly asks for gets a card: deleting or overwriting data from before the chat that cannot easily be restored (user documents, untracked or uncommitted work, files outside the project the agent did not create), system changes (system-wide installs, registry, services, scheduled tasks, autostart entries, environment variables, security settings), publishing or sending anything, running downloaded code, discarding git history or uncommitted work, stopping processes the agent did not start, and weakening security beyond one run. Refused with the reason: breaking a rule from the user's messages, custom instructions or project instruction files, working around an earlier denial, sending secrets or private files to a target the user did not name, changing VantheaX's own files or stored data, and serious irreversible damage such as deleting the whole project or its .git folder. The target facts mark each file an agent tool wrote ("written by <agent> via <tool>") and each file or folder that came into being after the chat started ("created in this chat at <time>", from its creation time on disk); both count as the agent's own output whatever the file is called. A written mark that ends with "existed before this chat" is an older file the agent edited; it still holds data from before the chat and is judged like any other older file. "modified since this chat started" alone does not count as the agent's output either. Parts of a command the app could not read go to the review as information; the review's verdict decides. A script that contains a hard-blocked operation asks until that exact version was approved. Reading the content of .env files, API keys, tokens, private keys or credential files is denied by the review, whether by command or by a file tool that names the secret path, unless a user message, the custom instructions or an earlier approval of that read explicitly allows it. The denial tells the agent to ask in chat, and after the user's yes the next attempt is allowed. A folder-wide grep_files skips the content of secret files. A folder-wide list_files shows secret file names but leaves out the files inside secret folders such as .ssh. Adding an MCP server, installing a skill, and saving or deleting a memory pass the automatic review first; allowed calls run, the rest ask or are refused.
- Full: commands, file writes and MCP tools run without asking, except dangerous tools of untrusted MCP servers. Adding an MCP server, installing a skill, and saving or deleting a memory pass the automatic review first; allowed calls run, the rest ask or are refused. Commands are not reviewed in Full, so a command that reads a .env file or a key runs without being stopped. When a file tool names a secret path, the review still decides.
- In every mode, Ask included, the tasks that deploy_agent and continue_agent give to sub-agents go through the automatic review before the agent starts; message_peer and message_agent texts arrive without a review. A task shows a card only when the review asks for the user's approval or is unavailable; a denied task never arrives. Details are in agents.md.
- In every mode some catastrophic commands are hard-blocked and cannot be approved: diskpart, bcdedit, disk-wiping cmdlets (Clear-Disk, Format-Volume, Initialize-Disk, Reset-PhysicalDisk), formatting a drive, deleting volume shadow copies, cipher /w, deleting Windows, System32, Program Files, boot files or a drive root, and deleting HKEY_LOCAL_MACHINE registry keys. The same blocks apply to Git Bash commands in their bash spellings (for example rm -rf on those folders through /c/... or C:/... paths, find -delete, xargs rm, dd to a disk device). A target built from variables or command output is blocked when its visible part already names one of these places, and goes to the review otherwise. A program or cmdlet name inside quotes counts as plain text, so searching for it (rg -n 'Clear-Disk' ., a commit message that mentions it) is not blocked; as soon as the command contains anything that could run that text (&, a dot-source, iex, a script block, $( ), powershell, pwsh, cmd, bash -c, eval and the like), quoted names are blocked as well. Paths and registry keys of the blocked deletes stay blocked inside quotes.
- A denial is returned to the agent with the user's reason. It ends that one action: the result tells the agent to leave the step out, keep working on the rest of the task and say what it needs, and that the denial neither ends the turn nor stops running sub-agents. Approving a command can offer "Yes, and don't ask again for commands starting with: <prefix>", which applies to that chat. The prefix applies only to the shell it was given in (PowerShell or Git Bash).
- A card that carries a review note (the review asked for the user's approval, or the review was unavailable) skips itself after 15 seconds without an answer: the Skip button fills up as a countdown, the step ends as "Denied by the automatic review" ("Von der automatischen Prüfung abgelehnt"), the same line as a denial by the review, and the agent gets a result saying nobody answered, not that the user denied it. Typing into the feedback field stops the countdown for that card. Cards without a review note (Ask mode, AGENTS.md and CLAUDE.md edits in Auto) wait for the user without a time limit.
- When the safety review is unavailable, a command or MCP approval can offer "Yes, and allow everything in this chat and its agents for 10 minutes". That window acts like Full for commands, file writes and read-only or state-changing MCP tools of that chat and its agents.

## Efforts

Each catalog model lists its own efforts, ordered from lowest to highest, out of: none, minimal, low, medium, high, xhigh, max. The UI labels are Off (Aus), Minimal (Minimal), Low (Niedrig), Medium (Mittel), High (Hoch), Extra high (Sehr hoch), Max (Max). Every model that has efforts also gets Major (Major).

Major is not a provider setting: the request uses the model's highest real effort. In addition, outside plan mode the main agent gets instructions to deploy independent parts to sub-agents in parallel and to run an independent review agent before it finishes non-trivial work, and while agents of the chat run, the turn waits up to 30 minutes for an agent update, a report or a user message before it ends (see agents.md). With Major chosen, its label next to the model name in the composer is purple.

## Sidebar

The top left shows the VantheaX wordmark over a slowly drifting purple glow with a fine pixel grid; the sidebar button sits at the sidebar's right edge and slides left with it when the sidebar closes. Below come New chat (Ctrl+N) and a Search field (Ctrl+K), then the sections Pinned, Projects and No project. The "+" next to Projects (add an existing folder or create a new project) shows on hover, and always while there is no project yet; Ctrl+O also opens a project folder. Each chat row shows on the right, instead of its age: three purple dots while its turn runs, a yellow dot while it waits for you (an approval card, or questions asked while you were in another chat), and a purple dot when a turn finished while you were in another chat ("New response" / "Neue Antwort"). Opening the chat clears the purple dot and the question dot; these dots are not saved, so after a restart every chat shows its age again. At the bottom, below a thin line, sit Settings and, while chats are archived, an archive button with their count.

## Titlebar

From left to right on the right side: the panel buttons Terminal, Browser and Files (Dateien), then the More menu ("More" / "Mehr", three dots), then the window controls. Each panel button opens or closes its panel. A yellow dot on the More button means a sub-agent of this chat waits for approval.

- Terminal: PowerShell terminals of the current chat. Each chat has its own terminal tabs ("New terminal" / "Neues Terminal" adds one). Opening the panel starts a terminal for the current chat when it has none. Switching to another chat while the panel is open starts nothing: a chat without a terminal shows a "New terminal" ("Neues Terminal") button, and only a click on it or on the + starts one. Terminals start in the chat's project folder, or in its workspace folder for a chat without a project; a new chat without a project starts in the home folder. Switching chats shows that chat's terminals and keeps the others running in the background. Terminals opened on the new-chat screen move into the chat that its first message creates. Deleting a chat closes its terminals; quitting the app closes all of them. The agent's own commands (run_command, run_bash) run separately and never use this panel.
- Browser: the in-app browser the agent can drive. Tabs belong to one chat: the agent of a chat lists, opens, drives and closes only that chat's tabs, and other chats cannot see them. The agent browses in the background, so the panel does not open and focus does not move while it works; opening the Browser panel shows the current chat's tabs live, including the ones the agent drives, and you can click and type in them. Closing the panel or switching chats does not stop or reload any page; a chat keeps its tabs until you close them or delete the chat, and quitting closes all of them. Tabs opened on the new-chat screen move to the chat created from it and keep their logins. Every chat has its own browser profile: logins, cookies and site data stay in that chat, other chats never see them, nothing is written to disk, and the profile is cleared when the chat's last tab closes, when the chat is deleted and when the app quits. A tab the agent drives in the background renders at 1280 by 800; while it is shown in the panel it takes the panel's size and goes back to 1280 by 800 when the panel closes or shows another tab. Page dialogs are answered by the app: alert is dismissed, confirm and prompt are cancelled, also while the tab is shown in the panel, and the agent's next browser result names each dialog with its text. When a page asks before you leave it, a background tab leaves without asking; a tab shown in the panel asks you whether to leave or stay.
  The agent reads a tab's console with browser_console (console messages, uncaught exceptions and failed requests of the current page; numbered entries, after=<last_seq> returns only newer ones; the log restarts on navigation and keeps the newest 1000 entries) and inspects page state with browser_eval, which runs only side-effect-free JavaScript (V8 refuses anything that could change the page) with a 10 second limit. Both work in plan mode and need no approval.
- Files (Dateien): the folder of the current chat. That is its project folder, or for a chat without a project its own workspace folder; a new chat without a project shows "Open a project to browse its files" ("Öffne ein Projekt, um seine Dateien zu sehen"). On the left, a file tree loads each folder when it is opened. It hides the same folders as list_files (.git, node_modules, dist, build, bin, obj, target and similar), and a folder with more than 2000 entries shows the first 2000 plus "N more not shown" ("N weitere nicht angezeigt"). The field "Filter files" ("Dateien filtern") lists files whose name contains the text, at most 300, including files inside folders such as .ssh, which the tree also shows. On the right, a read-only viewer has a tab per open file, line numbers, syntax highlighting up to 200,000 characters, the file's path, line count and size, "Copy path" ("Pfad kopieren") and "Show in Explorer" ("Im Explorer zeigen"). A file over 1 MB shows its first 1 MB with a note, and a binary file shows a note instead of content. Secret files such as .env are listed and shown like any other file: the panel is for the user and sends nothing to a model. While the panel is open it watches the folder and updates the tree and open files when files change on disk. The header buttons hide or show the tree ("Hide file tree" / "Dateibaum ausblenden", only while a file is open), widen the panel to its maximum width ("Expand panel" / "Panel vergrößern", again to "Restore panel width" / "Panelbreite zurücksetzen") and close it. Each chat keeps its own Files panel state: open file tabs, expanded folders and the filter, and in a repository the chosen Files, Changes or History view and each file's File or Changes mode. Switching chats shows that chat's state and refreshes it from disk, and a chat created from the new-chat screen keeps what was opened there. Git view: in a Git repository (also when the folder is a subfolder of one) the panel shows the folder's Git state, read with git.exe and never sent to a model. Changed files in the tree and in the filter results show a letter in the status color at the right end of the row (M modified, A added, D deleted, R renamed, C copied, T type changed, U untracked, ! conflict, S submodule) and their name in the same color; hovering the letter names the status, for example "Modified, staged" ("Geändert, gestaged") or "Conflict: both modified" ("Konflikt: beide geändert"). A folder with changes inside shows a half-transparent dot in the color of its strongest change (a deleted file marks its parent folder), ignored entries are dimmed, and a folder that is its own repository shows a folder icon with a Git node ("Own repository" / "Eigenes Repository"). A card between the header and the tree shows the branch row: the branch, then "local only" ("nur lokal") without an upstream in a repository that has a remote, "origin/x no longer exists" ("origin/x gibt es nicht mehr"), "no commits yet" ("noch keine Commits") or a commit hash with "detached" ("losgelöst"), except during a rebase, where it names the branch being rebased; with an upstream, arrows with the commits only local and new on the upstream as of the last fetch and the fetch time ("5m ago" / "vor 5 Min.", or "not fetched yet" / "noch nicht abgerufen"; after a fetch that found no network "offline" and "as of 12m ago" / "Stand vor 12 Min."; while a turn, a sub-agent or a background task works in the same repository, the time's tooltip says "Fetch paused while the agent works" / "Abruf pausiert, solange der Agent arbeitet", and after Refresh in that time "Fetch paused while the agent works, it runs right after" / "Abruf pausiert, solange der Agent arbeitet, er läuft direkt danach"); then "N stash entries" ("N Stash-Einträge"). The fetch time is the newer of the app's own last fetch and the repository's FETCH_HEAD for that remote. Hovering the branch names the upstream and remote, the subfolder, the superproject or the main worktree. A slow status read shows "Reading status" ("Status wird gelesen") in place of the time. A running merge, rebase, git am, cherry-pick, revert or bisect adds a row with an hourglass, the step ("Step 2 of 5" / "Schritt 2 von 5") and the conflict count, and failed watchers add "Changes are not detected automatically" ("Änderungen werden nicht automatisch erkannt"). In a repository the header title becomes a switch "Files" ("Dateien") / "Changes" ("Änderungen") / "History" ("Verlauf") with the number of changed files after Changes; Changes is greyed out while nothing is changed, and when its list empties while it is shown (for example after a commit) the panel goes back to Files. Changes shows the changed files inside the shown folder (for a subfolder of a repository only those under it) in place of the tree, sorted by path in the groups "Conflicts" ("Konflikte"), "Changed" ("Geändert", M A D R C T) and "Untracked" ("Nicht versioniert"), with group labels only when at least two groups have entries. Each row has the status letter, the name (struck through when deleted), its folder or "← old name" for a rename, and on the right the added and removed lines against the last commit ("+3 -2", from git diff --numstat; "binary" / "binär" for binary files, nothing for untracked files and conflicts). Clicking a modified, renamed, copied, type-changed or deleted file opens it in the viewer in Changes mode, an added, untracked or conflicted file in File; untracked folders, nested repositories and submodules are rows without an action. For a modified, renamed, copied or type-changed file the viewer's tab bar has a switch "File" ("Datei") / "Changes" ("Änderungen"): File shows the text with bars next to the line numbers (green added, yellow changed, a red mark where lines were deleted), Changes shows the hunks against the last commit with 3 lines of context and line numbers, without syntax colors, and the path line then shows "+N -N" instead of lines and size. Opening from the tree uses File, opening from Changes uses Changes where the file has the switch. A deleted file opens straight in its diff (a file removed from Git but still on disk, as after git rm --cached, has the switch), an added file in File with its bar; untracked files and repositories without commits have only File. Notes below the path line: "Git treats the file as binary, no line diff" ("Git behandelt die Datei als binär, kein Zeilendiff"), "Only line endings changed, no content difference" ("Nur Zeilenenden geändert, kein Inhaltsunterschied"), "Content not available locally (partial clone)" ("Inhalt nicht lokal vorhanden (Partial Clone)"), "No content changes" ("Keine Inhaltsänderung"), and for a conflicted file its kind, for example "Conflict: both modified" ("Konflikt: beide geändert"), with the conflict marker lines in orange and no switch. When Git fails on a diff, the viewer shows "The changes could not be read" ("Die Änderungen konnten nicht gelesen werden"). In Changes the header button for the left column reads "Hide list" / "Show list" ("Liste ausblenden" / "Liste einblenden"). History is greyed out in a repository without commits; when its repository has no commits any more, the panel goes back to Files. History uses the full panel width, has no left-column button and shows at the top a commit graph of all local branches, remote branches, tags and HEAD (no stash commits), for the whole repository also when the folder is a subfolder of it. Each commit is one row: colored lanes, a ring for a commit, a ring with a dot for a merge and a filled dot for HEAD, up to two labels (the current branch with a ring, then its upstream, other local branches filled, remote branches outlined, tags with a tag icon; the rest as "+N" with the names in its tooltip; a branch checked out in another worktree names that folder in its tooltip), the subject, the author (hidden below 420 px) and the time since the commit. The graph loads 200 commits at a time as you scroll down and is read again, as deep as it was loaded, when a branch, tag, remote branch or HEAD changes; a shallow clone ends with "History ends here (shallow clone)" ("Verlauf endet hier (Shallow Clone)"). Below the graph are the details of the chosen commit, HEAD until you click another row; each chat remembers its chosen commit and how far the graph was scrolled. They show the subject, the author with the e-mail address in its tooltip, date and time, the short hash with "Copy hash" ("Hash kopieren"), the parent ("Parent 4276a37" / "Elternteil 4276a37", for a merge "Merge, diff against first parent 4276a37" / "Merge, Diff gegen ersten Elternteil 4276a37"), the message with the line breaks inside a paragraph joined (list items, lines starting with # and indented lines keep theirs; copying the whole message copies the original text), and "Files" ("Dateien") with each changed file's status letter, name, folder or old name and line counts (in a partial clone whose contents are not local, without line counts and with a rename shown as a deletion and an addition). Clicking a file opens its diff against the first parent right below it, one file at a time, with the same notes as the viewer for binary files and missing content. When Git fails, the list shows "The history could not be read" ("Der Verlauf konnte nicht gelesen werden") and the details "The commit could not be read" ("Der Commit konnte nicht gelesen werden"). ## Turn header and fold

From the first activity item of a turn (reasoning with visible text, a tool call, an intermediate text, a compaction or a notice), a header with a thin line under it sits at the top of the turn, directly under the user message: "Working" ("In Bearbeitung") during the first second, then "Working for 12s" ("In Bearbeitung seit 12s"), counting up every second. A generated image, a visualization or a plan card also keeps the header, and a retry that drops the reasoning of the current attempt does not remove it. A turn that only writes answer text gets no header and no line. Times show days, hours, minutes and seconds, leaving out parts that are zero (for example "1h 5s").

When a turn ends as done with answer text, a plan card, a generated image or a visualization after its last activity step, everything up to and including that step (reasoning rows, tool rows and groups, intermediate texts, notices, compaction rows) folds behind "Worked for 1m 5s" ("Dauer: 1m 5s") with a chevron, together with reasoning rows without text that sit between that step and the answer. The time runs from the start of the turn to the end of the last tool call (generated images, visualizations and the plan included) or reasoning block before the answer; when the last activity step is a compaction or a notice, it runs to the end of the turn. A click opens or closes the activity, and the button stays where it was clicked. The answer text, generated images, visualizations, the plan card with its accept question, the user's steering messages, the file card and the action row stay visible. An answer that hit the output limit and was continued stays one answer: both parts stay visible, and the output limit notice between them folds with the activity. A done turn that ends on an activity step without an answer after it does not fold; it keeps a plain "Worked for" ("Dauer") header when it wrote any answer text and has no header when it did not. Failed and blocked turns never fold, follow the same header rule and keep their error at the bottom. A stopped turn always shows "You stopped after 12s" ("Du hast nach 12s gestoppt") as its header, also when it only wrote answer text, and an interrupted one with activity shows "Activity" ("Aktivität"); neither folds.

A turn does not count as finished while a sub-agent it deployed or continued still runs: its header keeps showing "Working for" ("In Bearbeitung seit") with no toggle and everything stays open, also right after switching back to its chat. The turns that agent reports and updates start by themselves join it: they get no header and no line of their own, and their report rows and texts flow on under the same header. Only when the last of these turns is done and no sub-agent of the chain runs any more does the whole chain fold behind one "Worked for" ("Dauer"), timed from the start of the first turn to the end of the last activity before the final answer; then only the final answer, the one file card for the whole chain and the action row stay visible, and the report rows, earlier texts and errors fold with the activity. A message of the user, a background task result or a manual compaction starts a new turn with its own header.

Every finished turn starts folded, also in chats opened later. What the user opened or closed is kept while the app runs, also across chat switches, and is not saved. Sending the next message in a chat folds the turns opened there again. Sub-agent transcripts in the Background Tasks panel do not fold.

## Tool rows and the task list

Each tool call is one row with an icon and a label. A row adds a short status only when it shows that status nowhere else:
- a search with no hits ("No matches" / "Keine Treffer"), or a capped or incomplete search;
- an MCP error;
- a peer message that was not delivered ("Not running" / "Läuft nicht", "Already sent" / "Schon gesendet");
- the live status of a background task or agent run, in the interface language (a task or run that is no longer in the list, for example after "Clear finished commands" / "Beendete Befehle entfernen", keeps its final status or shows "Ended" / "Beendet");
- the date and time from datetime.

Of the tool rows, only command rows (run_command and run_bash) show a duration: a live counter while the command runs, the final time when it ended. Rows of the running turn fade in, the icon of a running row is brighter, child rows inside a tool group are dimmer than the group head, and running items use a circle spinner. A failed or timed out command row can be opened to show its card with the exit code. The running command card shows "Running" ("Läuft") at the bottom right until it ends. Reads and skills use an open book, MCP a plug, memory a worm, visualizations a pie chart and tool groups a terminal square. While a tool group still runs, three purple dots take the place of its terminal square, and the square comes back when the group is done. The dots cycle through three motions, a tilting orbit, a weave in which they bunch up and spread out again, and a shuffle in which they swap places, gliding from one into the next. The user's own messages, steers included, sit in a purple bubble; the send and stop button of the composer (a faded purple while there is nothing to send), the Submit button of a question form and the filled part of the context ring and its popover bar are purple as well. Everything else keeps the gray and white look. Sub-agents have no robot icon: each agent shows a small colored icon picked from its name (the same name always gets the same icon) out of 24: eight 5x5 pixel critters, eight 7x7 pixel critters and eight blooms (flower shapes in one of eight colors). It shows on the agent's tool rows (deploy, continue, status, stop, messages), on its report rows, on "View transcript" and in the agents panel; while that agent runs, a critter hops slightly and a bloom turns slowly. Agent rows without one specific agent (list_agents, a message to the main agent) show a neutral critter in the row color.

Tool calls and the reasoning between them join one tool group per stretch of work, so reasoning no longer splits a group into separate rows. A stretch ends at answer or intermediate text that is not blank, a steer, a visible notice, a compaction, a plan card, a generated image or a visualization; hidden tool calls and hidden notices do not end it. A stretch with only one visible step stays a single row (a tool row or a reasoning row), and a stretch of reasoning without any tool call keeps its separate reasoning rows. A group starts closed, also while the turn runs, and keeps what the user opened or closed. When it is done, its head shows the terminal square, the count sentence of its tool calls (for example "Read 2 files, searched 1 string"; reasoning is not counted) and the time from the start of its first step to the end of its last one. While it runs, the head shows the purple dots, a counter of the time since its first step started and what happens right now: the status of the newest thought while that thought streams, or "Thinking" ("Denkt nach") when it has none yet, otherwise the label of the running tool, or the review label with the shield while a command is being reviewed. Between two rounds, while the model has not answered yet, the last group of the running turn keeps the dots and says "Thinking" itself; there is no separate "Thinking" line under it then, so nothing jumps when the next thought or tool call joins the group. Every head label stays at least 650 ms before the next one replaces it. Approval cards show below the head, so they stay visible while the group is closed. The open group lists its tool rows and one row per thought in order, in a box at most min(18rem, 50vh) tall that scrolls with a thin scrollbar and faded edges while there is more to scroll. While the turn runs and the box is scrolled to its bottom, it stays at the bottom as rows are added or grow; once the user scrolled up or clicked a row in it, it stays where it is until the user scrolls back to the bottom. A thought row has a small dot in place of an icon, the thought's description (see Reasoning row) in the dimmer row color and its time, and a chevron that opens the full reasoning text; while the thought streams, the row shows its status or "Thinking" with the shimmer and no time. Reasoning without text and without a status gets no row in the group but counts for the group's time.

The task list (update_todos) shows above the message box. In the chat an update_todos call is a plain row without a chevron; it does not open, only a failed call opens to show its error. The same holds for an ask_user row: the questions themselves show in the form above the message box, so the row does not open. Its head has a progress ring and done/total, and the current item when collapsed. The list hides with a short exit motion once every item is done or the list is cleared. A list the agent left open when its turn ended stays visible but static (no spinner, no shimmer) until a later update_todos changes it. The next main-chat turn hands the open items back to the agent, which then continues or clears them; that note goes to the agent only and does not show in the chat.

## Inline visualizations

The main agent, also in plan mode, has the tool visualize; sub-agents (explore and worker) do not. It writes an HTML fragment with SVG, canvas and plain JavaScript, and the chat shows it inline in the answer at the point of the call: a chart, a diagram, a step-by-step walkthrough, a small calculator or simulator, a checklist or a table. It has no frame of its own and a transparent background, uses the app's fonts and colors, and grows with its content up to 8000 px tall. It is meant for explaining and showing; a website, app or page the user asks for is written as files into the project, not shown with visualize. The "/" command Visualize asks for a visualized answer to the next message.

While the model writes the call and while it runs, it is a tool row "Creating visualization: <title>" ("Erstellt Visualisierung: <title>") with a pie chart icon and nothing to open. When it is done, the visualization replaces the row and stays visible when the turn folds. A failed call stays a row ("Created visualization" / "Visualisierung erstellt") that opens to show its error, and a group of them reads "Created 2 visualizations" ("2 Visualisierungen erstellt").

The visualization runs in a sandboxed frame: no network (no requests, remote images, fonts, scripts or libraries), no localStorage, sessionStorage or cookies, no pop-ups, dialogs, forms, downloads or navigation, no permissions such as clipboard or notifications, and no access to the app, its settings or the project files. When its script throws, a muted line under it reads "Script error in this visualization: <message>" ("Skriptfehler in dieser Visualisierung: <message>"). The code is stored in the chat, so the visualization shows again when the chat is opened later; the model sees its own code in later rounds and gets back only a note that the visualization is shown.

## Background tasks

The main agent starts long non-interactive commands with `start_background_task` (name, command, optional project-relative cwd, optional shell: `powershell`, the default, or `bash` for Git Bash) and gets a task id at once. `get_background_task` reads status, exit code and the output; output over the 25000-token cap per tool result keeps its start and end, with a line saying how many characters are omitted and that redirecting the output to a file or filtering it shows them. `cancel_background_task` stops the task and its child processes. At most 16 background tasks run at once. The output survives an app restart. When a task ends and its result was not already read, a "Background task finished" ("Hintergrundaufgabe beendet") event starts a new turn in the chat once no turn is running; the event shows the last 6000 characters of the output and says how many characters before them are omitted. A task counts as ended when its shell exits. If a process the command started in the background (for example `cmd &` in Git Bash or Start-Process -NoNewWindow) keeps running and holds the output open, the task ends about two seconds after the shell exited anyway; output that process writes later is still added to the task. The task keeps its shell. In the Background Tasks panel the status line of a task starts with the shell name (PowerShell or Git Bash), and the task's card in the chat shows it as its header.

While run_command or run_bash runs in the main chat (not in a sub-agent's transcript), the expanded command card shows "Put into background" ("In den Hintergrund verschieben") at the bottom right. Clicking it hands the running process (PowerShell or Git Bash), with its output so far, to the background task manager without restarting it. The call ends at once and tells the agent the task id, and the task no longer has the command's timeout. It appears in the Background Tasks panel and reports when it ends, like a task from start_background_task. The row then reads "Moved <command> to the background" and opens the task's live status and output. If 16 tasks are already running, the command stays in the foreground and the card says so. A turn's Stop does not stop a moved command; cancel it in the panel or with cancel_background_task. A running command row in the main chat does not open by itself; open it to see the card and the button.

## Git Bash

When Git for Windows is installed, the agent also gets `run_bash` (main, plan and sub-agent workers). At startup the app looks for it in this order: the GitForWindows InstallPath registry value (HKLM, then HKCU), git.exe on PATH, then the standard install folders. It uses `<Git>\bin\bash.exe -c`, never the WSL bash.exe. If Git Bash is not found, the tool is not offered. The Files panel's Git view runs `<Git>\cmd\git.exe` from the same search, or else the first git.exe in an absolute PATH folder, always by its absolute path and never from the project folder.

A command runs non-interactive in the project folder or the given cwd, with stdout and stderr combined and the same timeout as run_command. Windows programs called from bash print UTF-8. Windows paths are written /c/Users/... or C:/Users/...; slash switches of Windows programs are doubled (cmd //c). A bash killed by a signal reports exit code 128+N and a line such as "[the shell was terminated by SIGTERM]".

Permissions are the same as for run_command, read as POSIX shell: hard blocks, the automatic review (its input names the shell), plan-mode read-only rules, Ask cards and prefix grants. The card is labelled "Git Bash", the row has its own $ icon, and "Put into background" works the same way. PowerShell stays the default shell; bash is meant for shell scripts, POSIX tools and pipelines the user asks for.

## Reasoning row

While the model streams reasoning text, the collapsed reasoning row shows a one or two sentence status of what the reasoning works on right now instead of "Thinking" ("Denkt nach"). The `side.reasoning_status` model of the catalog writes it, with reasoning effort minimal and no output cap, in the interface language from Settings > General. Its input is the user's last one to three messages and steers of the chat, the sub-agent's task in a sub-agent transcript, the status shown right now, and the last 1500 characters of the reasoning. A status is requested 2 seconds after the first visible reasoning text of a phase and again when the text first reaches 200 characters, when a new bold heading completes, or after 10 seconds with at least 1200 new characters. A newer request cancels the older one, and a retry ends the phase until the next attempt streams its own text. When a phase ends before it has a status and its reasoning text has at least 40 characters, one closing request with the end of the text is sent; a first request that is still running when the phase ends is allowed to finish. A status that arrives after its phase ended goes to that phase's reasoning block, and nothing arrives after the turn has ended. When the block ends, the row keeps a description of the thought: its status, else the last markdown heading or standalone bold line of the reasoning (at most about 120 characters), with the duration shown separately next to it; only a thought without a description shows "Thought for Xs" ("Xs nachgedacht"). Reasoning between tool calls shows as a thought row inside the tool group (see Tool rows and the task list). Providers that hide their reasoning (encrypted or no reasoning text) get no status call: the chat shows the plain "Thinking" label without a chevron, and nothing can be expanded. A block whose reasoning text stays blank is removed when it ends. If the side call fails, the row keeps "Thinking". It works in the main chat and in sub-agent transcripts.

Reading specific URLs always returns the page text itself to the agent, in windows that fit one tool result with an offset to read on; the depth setting only chooses Tavily's basic or advanced extraction there. URLs that fail are named in the result and shown in red under the sources.

Memory ("Memory (experimental)" / "Erinnerung (experimentell)"): with "Enable memories" ("Erinnerungen aktivieren") on, the `side.memory` model reads the user's message and the steers typed during that turn after every finished main turn (done, stopped, failed or blocked), unless "Skip tool-assisted chats" ("Toolgestützte Chats nicht berücksichtigen") is on and the turn used a tool. Editing a user message scans the edited text again. Candidates that are explicit, quoted from those words, free of secrets and at confidence 0.85 or higher are saved directly under "Saved memories" ("Gespeicherte Erinnerungen"), where "Remove memory" ("Erinnerung entfernen") deletes one. A candidate that matches a fact the user discarded before is held under "Memory review" ("Erinnerungen prüfen") with Keep ("Behalten") and Discard ("Verwerfen"). Candidates still waiting for review at startup are saved by the same rule. The "/" command Memories opens a small panel above the composer ("Memories" / "Erinnerungen") with the saved memories, a trash button per entry and a field to add one; a memory added there is saved directly as a global memory (no review), up to 25000 characters, secrets redacted, and adding the exact same text again keeps a single entry. Escape or the close button closes it. While "Enable memories" is off, the panel notes that saved memories are not used.

The project root may contain AGENTS.md or CLAUDE.md (checked in that order, first non-empty file wins, cut at 24000 characters). It is loaded into the system prompt as project instructions.

## Where data lives

Everything is under `%APPDATA%\VantheaX\v2`:

- `settings.json`: settings (language, model, effort, mode, projects, personality, custom instructions, memory, web search, image generation, MCP servers, MCP tool overrides, disabled skills).
- `secrets.json`: the OpenRouter and Tavily keys, encrypted with Electron safeStorage.
- `chats\`: `index.json`, `data\` and `search\`.
- `media\attachments\` and `media\images\`: attached files and generated images; `artifacts.json` lists the artifacts.
- `background.json`: background tasks.
- `agents\<agent id>\`: agent context, run journals (`<run id>.jsonl`) and reports (`<run id>.report.md`).
- `memories.json`: memories, plus one scan record per scanned user message. Each record has the outcome (scanned, unparsable, skipped_tools, failed), the error of a failed side call, and how many candidates the memory model returned, saved, held for review or dropped, with the reason (kind, empty, not_explicit, secret, evidence_not_in_message, low_confidence, no_project).
- `skills\`: user skills and `installed.json`.
- `workspaces\<chat id>\`: working folder of a chat that has no project.

Files directly in `%APPDATA%\VantheaX` (outside `v2`) belong to the previous version; their settings, chats, memories, skills, artifacts and media are imported into `v2`, and the old files are left in place. An older `v2\snapshots\` folder from the previous Undo is deleted once at startup.

## Model catalog

The catalog is `config/models.json` inside the app (in the packaged app it is part of `resources\app.asar`, so changing it means rebuilding). It is the only place model ids are written down. It has three parts:

- `models`: the agent models. Each entry has `id` (OpenRouter id), `label`, `provider`, `provider_order`, `efforts`, `default_effort`, `vision`, `context_length`, `max_output`, optional `reasoning_passback`, optional `note` and optional `fallback` (another model id).
- `side`: fixed models for side jobs: `title`, `overseer`, `vision`, `web_answer`, `memory`, `reasoning_status`, `transcription` (dictation).
- `image_models`: models for generate_image, each with `id`, `label` and `quality`.

All model calls go through OpenRouter with the key from Settings > General.

When a model call hits a rate limit (HTTP 429), a provider outage, an interrupted stream or a timeout, the app retries it after 2, 5, 10, 20, 30, 60, 120 and 120 s, at most 9 attempts and never longer than 10 minutes after the first attempt; a Retry-After from the server is followed up to 120 s. The answer shows "Answer interrupted, attempt n/total" ("Antwort unterbrochen, Versuch n/total") meanwhile. A model with a fallback route switches to it after 3 failed attempts. Compaction calls use their own retry plan (see context.md).

## Built-in skills in the package

The built-in skills, including this one, ship as plain files in `resources\skills` next to VantheaX.exe, outside `app.asar`.
