# Settings, data locations and the model catalog

## Settings

Sections: App group with General (Allgemein: Language, OpenRouter API key, Key balance, and under Notifications / Benachrichtigungen the switch "Notification sound" / "Benachrichtigungston", on by default: while the VantheaX window is not focused, a short soft chime plays when a main-agent turn ends for any reason except the user's Stop, including provider errors, and a slightly brighter one when the main agent asks the user a question or shows an approval card; sub-agents never chime, and chimes closer than two seconds apart play once) , Personalization (Personalisierung: Personality, Custom instructions, Memory) and Privacy (Datenschutz: under "Chats and projects" / "Chats und Projekte", "Archive all chats" archives every chat except those with a running turn, "Delete all chats" deletes every chat including archived ones with their attachments, and "Remove all projects" removes every project and deletes its chats while the folders on disk stay (worktree folders of deleted chats are deleted, their branches stay); each asks for confirmation first and then shows how many it handled); Integrations group (Integrationen) with Web search (Websuche, Tavily API key), Image generation (Bildgenerierung), MCP servers (MCP-Server), Hooks (see hooks.md) and Skills (see skills.md). In the rail on the left the highlight slides to the chosen section, and on a narrow screen a tapped section scrolls into view.

MCP servers has "Add server" ("Server hinzufügen") next to its heading. The add dialog has a label above each field (Name, Command ("Befehl"), Arguments ("Argumente"), Environment ("Umgebung"), "Working folder (optional)" ("Arbeitsordner (optional)")) and example values as placeholders, with the command and the working folder in Consolas. A server's "Tools" section shows only when the server offers tools, and an empty server list shows nothing.

Web search: a search returns the matching sources with the relevant excerpts of their text (Tavily basic search, no second model); results carry their publish date when Tavily knows it, and the agent can ask for news and a time range per search. Reading specific URLs always returns the page text itself to the agent, in windows that fit one tool result with an offset to read on (Tavily basic extraction). URLs that fail are named in the result and shown in red under the sources.

Memory ("Memory (experimental)" / "Erinnerung (experimentell)"): with "Enable memories" ("Erinnerungen aktivieren") on, the `side.memory` model reads the user's message and the steers typed during that turn after every finished main turn (done, stopped, failed or blocked), unless "Skip tool-assisted chats" ("Toolgestützte Chats nicht berücksichtigen") is on and the turn used a tool. Editing a user message scans the edited text again. Candidates that are explicit, quoted from those words, free of secrets and at confidence 0.85 or higher are saved directly under "Saved memories" ("Gespeicherte Erinnerungen"), where "Remove memory" ("Erinnerung entfernen") deletes one. A candidate that matches a fact the user discarded before is held under "Memory review" ("Erinnerungen prüfen") with Keep ("Behalten") and Discard ("Verwerfen"). A group without entries is left out, unless it could not be loaded. Candidates still waiting for review at startup are saved by the same rule. The "/" command Memories opens a small panel above the composer ("Memories" / "Erinnerungen") with the saved memories, a trash button per entry and a field to add one; a memory added there is saved directly as a global memory (no review), up to 25000 characters, secrets redacted, and adding the exact same text again keeps a single entry. Escape or the close button closes it. While "Enable memories" is off, the panel notes that saved memories are not used.

The project root may contain AGENTS.md and CLAUDE.md. Every one that is not empty is loaded whole, without a length limit, into the system prompt as project instructions, after the built-in sections and the custom instructions; they take priority over the agent's defaults where they apply. In a worktree chat, a file that is missing in the worktree is read from the same place in the main checkout.

Agents that can write files get code rules in the system prompt: names without g_, m_, s_ or k prefixes, values written where they are used instead of a block of named constants (a constant only when several places share the value or it belongs to a protocol, file format or public interface), the default indentation, and more, plus a separate comment rule: no comments except a one-line reason the code cannot show, and never divider or banner lines, section titles, file headers or commented-out code, in any language. The write_file and replace_in_file descriptions tell the agent to read these rules again before it writes code. In an empty project, or one with no instruction files and no existing code that sets a style, these rules are the whole code style unless the user or the custom instructions set another: the agent follows every one of them, the style rules included, and before it finishes it reads every file it wrote again and checks it rule by rule. Only the user's messages, the custom instructions, the project's AGENTS.md or CLAUDE.md and a convention the project's existing code clearly follows override them; when the user's messages or custom instructions conflict with the style of the existing code, the user wins. After every write_file of a code file, an automatic check looks for newly added names with a g_ prefix and new separator or banner comment lines (a run of ten or more `=`, `-`, `#`, `*`, `~` or `_`). When it finds some, a note is appended to that tool result for the agent: the style is off by default unless the user, the custom instructions, the project's instruction files or its existing code ask for it. The note comes at most twice per chat (each sub-agent counts on its own) and is not shown in the chat view; replace_in_file is not checked.

## Where data lives

Everything is under `%APPDATA%\VantheaX\v2`:

- `settings.json`: settings (language, model, effort, mode, projects, personality, custom instructions, memory, web search, image generation, MCP servers, MCP tool overrides, disabled skills, hooks).
- `secrets.json`: the OpenRouter and Tavily keys and the Phone access pairing key, encrypted with Electron safeStorage.
- `chats\`: `index.json`, `data\` and `search\`.
- `media\attachments\` and `media\images\`: attached files and generated images; `artifacts.json` lists the artifacts.
- `background.json`: background tasks.
- `scheduled-tasks.json`: scheduled tasks (see scheduled.md); a task's name and project are those of its chat.
- `agents\<agent id>\`: agent context, run journals (`<run id>.jsonl`) and reports (`<run id>.report.md`).
- `memories.json`: memories, plus one scan record per scanned user message. Each record has the outcome (scanned, unparsable, skipped_tools, failed), the error of a failed side call, and how many candidates the memory model returned, saved, held for review or dropped, with the reason (kind, empty, not_explicit, secret, evidence_not_in_message, low_confidence, no_project).
- `skills\`: user skills and `installed.json`.
- `reads\<chat id>.json`: per agent of the chat, the SHA-256 of every file it last read or wrote, which write_file and replace_in_file compare before they change a file.
- `workspaces\<chat id>\`: working folder of a chat that has no project.
- `worktrees\<id>\<folder>\`: the worktree of a chat that works in its own worktree; `worktrees\ledger.json` records worktree creations and deletions until they finish.
- `turn-diffs\<chat id>\`: the turn diff snapshots of a chat (see Diff view in the Files panel in interface.md): `index` and `objects\`, a Git index and object store with every file version the snapshots saw that the repository does not already have (changed tracked files and untracked files Git does not ignore, `.env` included when it is not ignored); `turns.json` with one record per turn (start and end snapshot, mode, late work); `summaries.json` with cached file lists per pair of snapshots; and in a folder without Git `recorded\<message id>\` with the bytes of the files the agent's file tools wrote, before and after. It is deleted with the chat, a fork gets the parent's snapshots (objects hardlinked), and folders of chats that no longer exist are removed at startup. Nothing in it leaves the machine.

Outside `v2`, every chat gets a scratchpad folder `%TEMP%\VantheaX\scratchpad\<random GUID>` the first time a prompt is built for it in a run of the app. It is for the agent's throwaway files such as test scripts and probes; read_file, get_file_outline, view_image, write_file and replace_in_file accept absolute paths inside it, with the same approvals as files in the project. Each chat only reaches its own scratchpad. The folder is deleted when its chat is deleted or the app closes, and the chat gets a new one in the next run, so nothing that must last belongs there.

Files directly in `%APPDATA%\VantheaX` (outside `v2`) belong to the previous version; their settings, chats, memories, skills, artifacts and media are imported into `v2`, and the old files are left in place. An older `v2\snapshots\` folder from the previous Undo is deleted once at startup.

## Model catalog

The catalog is the folder `config/models` inside the app (in the packaged app it is part of `resources\app.asar`, so changing it means rebuilding). It is the only place model ids are written down. `index.json` holds `model_files`, `side`, `side_models` and `image_models`; the agent models live in one file per OpenRouter vendor, named after the prefix of their ids (`openai.json`, `google.json`), each an array of entries. It has four parts:

- `model_files` and the files it names: the agent models. The Model picker lists them in the order of `model_files`, then in file order; a new vendor file loads only once its name is in that list. Each entry has `id` (OpenRouter id), `label`, `provider`, `provider_order`, `efforts`, `default_effort`, `vision`, `context_length`, `max_output`, optional `reasoning_passback`, optional `verbosity` (low, medium, high, xhigh or max, sent as OpenRouter's verbosity parameter; the GPT-6 models use low, which makes their answers shorter), optional `note` and optional `fallback` (another model id), optional `tiers` (`fast`, `ultrafast` or `flex`, each a list of routes that replaces `provider_order` for that tier, or an object with `provider_order`, an optional `id` when the tier is another OpenRouter model and an optional `max_output` when the tier's endpoint allows fewer output tokens) and optional `default_context` (`limit`, null for the full window, and `compact_percent` from 50 to 95), which applies until the user sets that model's Context limit or Auto-compact. `provider_order` lists OpenRouter provider slugs or exact endpoints (for example `relace/fast`) that OpenRouter tries one after another; no other provider is used. DeepSeek V4.1 Flash goes to DeepSeek first and to Relace's fast endpoint when DeepSeek fails. With several routes the strictest documented image and request size limit among them applies, so DeepSeek V4.1 Flash requests stay under Relace's 8 MiB even when DeepSeek answers.
- `side`: fixed models for side jobs: `title`, `overseer`, `vision`, `memory`, `reasoning_status`, `transcription` (dictation), `git_text` (commit messages and pull request text in the Files panel).
- `side_models`: the context window (`context_length`, `max_output`) of side models that are not agent models. The diff for `git_text` is sized to that model's window minus its output.
- `image_models`: models for generate_image, each with `id`, `label` and `quality`.

All model calls go through OpenRouter with the key from Settings > General.

When a model call hits a rate limit (HTTP 429), a provider outage, an interrupted stream, a timeout or a broken empty answer (no text and no tool call, with the provider's finish reason MALFORMED_RESPONSE, MALFORMED_FUNCTION_CALL or UNEXPECTED_TOOL_CALL, or OpenRouter's finish reason error; Gemini models send these now and then), the app retries it after 2, 5, 10, 20, 30, 60, 120 and 120 s, at most 9 attempts and never longer than 10 minutes after the first attempt; a Retry-After from the server is followed up to 120 s. The answer shows "Answer interrupted, attempt n/total" ("Antwort unterbrochen, Versuch n/total") meanwhile. A model with a fallback route switches to it after 3 failed attempts. Compaction calls use their own retry plan (see context.md). When OpenRouter answers 402 with the number of output tokens the balance or key limit can still afford (it checks this even for requests that run on the user's own provider key), the app sends the round again with that number, and again with each smaller number OpenRouter names; below 64,000 affordable tokens it stops and shows the credits error.

## Built-in skills in the package

The built-in skills, including this one, ship as plain files in `resources\skills` next to VantheaX.exe, outside `app.asar`.
