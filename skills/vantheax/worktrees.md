# Worktrees

## Worktrees

A new chat in a project that is a Git repository can work in its own worktree instead of the project folder: a separate checkout on its own branch, so its edits, builds and commits never touch the main checkout. The choice is made in the "+" menu of a new chat (Worktree); an existing chat keeps the folder it works in. It needs Git for Windows 2.33 or newer, a repository with at least one commit, and a project folder that is in the last commit. A repository whose own configuration sets a filter (filter.*, for example from git lfs install --local) gets no worktree, because the checkout would run the filter's program: the Worktree row shows "Repository configuration starts programs (filter.lfs), use a terminal" ("Repository-Konfiguration startet Programme (filter.lfs), nutze ein Terminal"), and Restore worktree fails with the same reason. A project that is a subfolder of a repository gets the whole repository as its worktree and works in the same subfolder of it.

- Branch: `vx/` plus the first five words of the first message in lowercase ASCII (for example `vx/fix-the-login-bug-in`), or `vx/chat-` plus six characters of the folder id when the message has no letters or digits. A taken name gets `-2`, `-3` and so on. The branch starts from the commit the main checkout is on, also a detached one; uncommitted changes of the main checkout are not carried over. The repository's hooks do not run when the worktree is created.
- Folder: `%APPDATA%\VantheaX\v2\worktrees\<8 hex characters>\<repository folder name>`. The chat's turns, sub-agents, background tasks, terminals and the Files panel with its Git view all work there.
- node_modules: when the project folder has a real node_modules folder, the worktree gets a junction to it, so it runs without a new install; npm install in a worktree chat therefore changes the main project's node_modules. The file tools read through that junction and never write through it.
- .worktreeinclude: a file at the repository root of the main checkout, in .gitignore syntax. Files that match it and that Git ignores, for example .env.local, are copied into a new worktree.
- Submodules stay empty in a worktree.
- AGENTS.md and CLAUDE.md: when one is missing in the worktree (for example a CLAUDE.md that Git ignores), the one at the same place in the main checkout is used, for the system prompt and for the automatic review. The main checkout here is the project folder itself, also when that folder is a linked worktree of another checkout; chats without a worktree read only their own folder.
- Memories, generated images, the sidebar group and the project settings stay with the project.
- Deleting the chat (also through Delete all chats or removing its project) deletes its worktree folder once the chat's turn and sub-agents have stopped, after at most 15 seconds of waiting; the junction is unlinked, never followed, and the branch with its commits stays. A fork shares the worktree of its chat, and the folder goes with the last chat that uses it. A creation or deletion that a crash or quit interrupted is finished at the next start; folders under `worktrees\` that no chat and no unfinished step names are left alone.
- Missing folder: when the worktree folder is gone, the chat never falls back to the main project. Messages, terminals and the Files panel refuse until the worktree is restored, which adds it again from its branch, links node_modules and copies the .worktreeinclude files again. Restoring fails when the branch was deleted. The Files panel then shows "This chat's worktree folder is missing" ("Der Worktree-Ordner dieses Chats fehlt") with the folder path and the button "Restore worktree" ("Worktree wiederherstellen", "Restoring worktree" while it runs); a failure shows "Restoring failed: <error>" ("Wiederherstellen fehlgeschlagen: <Fehler>") below it.
- Delete confirmations: the dialogs for deleting a chat (also an archived one), removing a project, Delete all chats and Remove all projects check the worktrees they would delete (a skeleton line while that runs). One chat: "Its worktree folder is deleted. The branch <branch> stays." plus, in orange, "The worktree on <branch> has N uncommitted changes. They are deleted with the folder." and "N commits are on no remote. They stay on the branch <branch>." when that applies. Several: "N worktree folders are deleted. Their branches stay." and, in orange, "N worktrees have uncommitted changes or commits on no remote: <branches>. Uncommitted changes are deleted, the branches stay." A worktree that a fork outside the deletion still uses is not mentioned, because it stays. When the check fails, the folder line shows with "Could not check the worktree for uncommitted changes." ("Der Worktree konnte nicht auf nicht committete Änderungen geprüft werden.").
- When the main project folder is renamed, the app repairs the worktrees' link to it with git worktree repair.
