# Headless mode, local API, SDK and CLI

## Headless mode

VantheaX can run without a window so that other programs (scripts, CI jobs, other apps) can use it. The same `VantheaX.exe` starts headless with `--vx-serve`. It then opens a local HTTP API, runs turns with the same engine, tools, permission modes and automatic review as the app, and gives back the streamed events and a final result. It is a separate process from the open app: both can run at the same time.

Switches: `--vx-serve` (headless), `--vx-port=<n>` (port of the API, default 0 so the system picks one), `--vx-data-dir=<absolute path>` (default `%APPDATA%\VantheaX-headless`) and `--vx-lease=stdin` (quit when stdin ends, so the instance never outlives the program that started it). Environment: `VANTHEAX_API_TOKEN` is required (at least 32 characters, never printed) and `OPENROUTER_API_KEY` holds the OpenRouter key; headless mode never reads the key from the app's settings. Both are removed from the environment at start, so commands and MCP servers the agent starts do not see them. When the API listens, one JSON line `{"vantheax":"ready","api":1,"url":"http://127.0.0.1:<port>","pid":<pid>}` goes to stdout. Exit codes: 1 a startup step failed, 2 bad switches or a missing token, 3 another process already uses the data dir; each comes with one JSON line on stderr. A headless instance also quits on `POST /v1/shutdown`; running turns then end as interrupted with error kind `app_closed`, and every open run gets its `run.settled` event before the event streams close.

The data dir is never the app's folder: a data dir equal to, inside or containing `%APPDATA%\VantheaX` is refused, also through a junction, a symbolic link or a short 8.3 name. Agent commands that delete or move files in the data dir or in `%APPDATA%\VantheaX` are blocked like commands on the app's own data, and so are shell commands that write into either folder (redirections, `Set-Content`, `Out-File`, `New-Item`, `Copy-Item`, `copy`, `xcopy`, `robocopy`, `tee`, `cp`, `touch`, `mkdir`, `dd of=`, `sed -i` and the like), also in mode full; neither folder can be a session's project folder. Its `data\v2\` has the same layout as the app's `%APPDATA%\VantheaX\v2` (settings, chats, media and the rest), `chromium\` holds the browser profile and `documents\` the documents folder. A new data dir starts with default settings, and the API cannot change settings other than the two billing switches (see ChatGPT plan and Claude plan below). Only one process can use a data dir at a time. The app does not show headless sessions, and a headless instance does not see the app's chats.

Off in headless mode: the window, the tray icon, dialogs, scheduled tasks (they do not run, and the scheduled task tools are hidden from the model), the computer use tools (hidden) and Phone access. The browser tools stay.

## Local API

The API listens on 127.0.0.1 only. Every request needs `Authorization: Bearer <token>`; requests with an `Origin` header (web pages) are refused with 403 and a wrong `Host` with 421. It has sessions (a chat bound to an absolute project folder), prompts, run results, stop, steer, approvals, questions, plan accept, the turn diff, attachment uploads, a server-sent event stream that can resume after the last event id, and shutdown. There is no route for other settings or keys; the account routes below switch the billing modes, run the ChatGPT sign-in and read the Claude Code login. A prompt returns a `run_id`. A run settles when the session is idle (no turn, sub-agent, workflow or background task still running); its result has the status, the final answer text, all assistant messages, open questions, pending approvals, a plan waiting for acceptance, the files the main turns changed and their token usage (edits and tokens of sub-agents are not in it; the session diff lists every changed file). Stop ends the main turn and its workflows; sub-agents and background tasks keep running, so a background task that never ends keeps the run open, and waiting only for the first turn is the way out. Each turn ends with exactly one `end` event, each run with one `run.settled` event.

## ChatGPT plan

A headless data dir has its own billing mode and its own ChatGPT sign-in, stored encrypted in that data dir; it never uses the desktop app's sign-in, so a headless instance is signed in once with the routes or CLI commands below. Four routes cover it: `GET /v1/account` returns the billing mode (`api` or `chatgpt`) and the ChatGPT account (status `signed_out`, `signing_in`, `signed_in` or `expired`, email, name, whether plan usage is enabled and the last error); `POST /v1/account/billing` with `{ "billing": "chatgpt" }` or `"api"` switches it; `POST /v1/account/chatgpt/sign_in` with the optional flags `fresh` (sign in another account) and `consent` (ask OpenAI again for plan usage) opens OpenAI's sign-in page in the browser of the machine that runs VantheaX and answers right away with status `signing_in`; `POST /v1/account/chatgpt/sign_out` signs out and revokes the refresh token at OpenAI. The outcome of a sign-in arrives as the event `account.changed`, which only streams without a session filter get. With billing `chatgpt`, `GET /v1/models` still lists the whole catalog and the default model stays the data dir's default; a prompt or session that names an OpenAI model the signed-in account offers runs on the plan, and `OPENROUTER_API_KEY` serves every other model (other vendors and OpenAI models the account does not offer) and image generation. The SDK has `client.account.get`, `set_billing`, `sign_in` and `sign_out`; the CLI has `vantheax account`, `vantheax billing api|chatgpt`, `vantheax sign-in [--fresh] [--consent]` (it prints that the sign-in page was opened in the browser of the machine that runs VantheaX and waits for the result) and `vantheax sign-out`.

## Claude plan

A headless data dir also has its own Claude switch (`claude_billing`, `api` by default), set like the desktop app's Claude models switch (see settings.md), with the same routing: with `claude` a prompt or session on a Claude model runs in Claude Code on the Claude plan, everything else as before. The Claude login is not per data dir: it is the host user's own Claude Code login, the one Claude Code keeps in the user's Claude folder, and VantheaX never stores Claude credentials. Headless mode has no terminal panel, so the user signs in by running the printed login command (`& '<path of the bundled claude.exe>' auth login --claudeai`) in PowerShell on the machine that runs VantheaX. `GET /v1/account` also returns `claude_billing` and `claude`, the Claude Code login (status `unknown`, `missing`, `signed_out`, `signed_in`, `other_login` or `error`, email, subscription, auth method, the login command and a detail); `POST /v1/account/claude-billing` with `{ "billing": "claude" }` or `"api"` switches it; `POST /v1/account/claude/refresh` reads the login state again. A change of the login state arrives as the event `claude.changed`, which only streams without a session filter get. The SDK has `client.account.set_claude_billing` and `refresh_claude`; the CLI has `vantheax claude-billing api|claude` and `vantheax claude`, which reads the login again, prints `claude: <status>` with the email and subscription, and when not signed in prints the login command to run on the host and exits with 1. `vantheax account` adds the lines `claude billing: <mode>` and `claude: <status>`.

## Approvals and questions without a person

A prompt chooses the permission mode (default Auto) and an approval policy:

- `reject` (default): nobody is asked. Every approval the main turn or a sub-agent would wait for is denied at once, and the model is told that the run has no one to approve actions and should continue without that action. In Auto everything the review allows still runs, so only steps the review wanted a human for are left out.
- `client`: approvals wait for the calling program, which sees them as events and answers or holds them, as a person would in the app. An approval the review raised skips itself after 15 seconds without an answer or a hold, as in the app.

To run without any approvals, a program uses mode Full. `ask_user` does not block: the model keeps working, the run can end done with the open questions in its result, and answering them after the turn starts a new run. The mode, model and policy of a prompt stay with the session for the turns that follow, question answers and plan accepts.

## SDK and CLI

The VantheaX source has a TypeScript SDK and the `vantheax` command line tool in `sdk/`, built with `npm run build:sdk` into `dist-sdk/`. `create_vantheax` starts a headless instance with a fresh token and the stdin lease and returns a client; `create_client` connects to a running one; `client.run(session_id, { text })` sends a prompt and waits for the settled result. `vantheax run "<prompt>" --cwd <folder>` does one prompt from a terminal or a CI job and prints the answer, or NDJSON with `--format json`; it always uses the `reject` policy, and its exit code is 0 only when the run ended done with nothing left to answer. `vantheax --help` prints the usage. `vantheax account`, `billing`, `sign-in`, `sign-out`, `claude-billing` and `claude` work on the same data dir or server (see ChatGPT plan and Claude plan above). Ctrl+C stops the turn, waits until it has ended, prints that result and exits with 130; a second Ctrl+C exits at once.

The full description (switches, every endpoint, the events, the SDK, the CLI flags, exit codes and a CI example) is `sdk/README.md` in the VantheaX source repository.
