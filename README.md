# VantheaX

VantheaX is a Windows desktop app for working on code together with a language model. You open a project folder, chat with the model, and it can read and change the files in that folder, run PowerShell commands (and Git Bash commands when Git for Windows is installed), search the web and hand bigger jobs to sub-agents running in the background.

It is built with Electron, React and TypeScript. The models come from OpenRouter, so you need your own OpenRouter API key.

## What it can do

- Read, search, edit and write files inside the project folder you picked. It stays inside that folder. It reads a secret file like `.env`, an API key or an SSH key only with your permission: in Ask you approve it on a card, in Auto the review refuses it until you allow it in the chat (the agent asks you first). In Full only the file tools are reviewed for this; a command that reads `.env` runs without being stopped. It never writes to secret files. While the model is still writing a file or an edit, you can open its row and watch the new text come in line by line.
- Run PowerShell commands, and Git Bash commands when Git for Windows is installed, with live output while they run. Long builds or test runs can go to the background in either shell, and the agent picks up the result when they finish. A running command's row counts up how long it has been running. In the main chat it stays closed until you open it; the open card shows the live output and "Put into background" at the bottom right, which moves the command to the background without restarting it.
- Plan mode: the agent only looks around and writes a plan, and nothing changes until you accept it. Turn it on or off with the Plan chip in the message box, in the "+" menu or with /plan; the chip is always there and is highlighted while plan mode is on.
- Questions while it works: the agent can ask you something above the message box without stopping. Pick an answer, write your own or close the question; your answer reaches the running turn, or starts a new one when it is done.
- Inline visualizations: when a picture explains something better than prose, the agent can put an interactive chart, diagram, step-by-step walkthrough, small calculator or table right into its answer, in the app's fonts and colors and as tall as its content. It runs in a sandbox with no network, no storage and no access to the app or your files. It is for explaining, not for building: a site or app you ask for is written as files into the project. Only the main agent makes them, not sub-agents. The "/" command Visualize asks for a visualized answer to your next message.
- A task list above the message box for longer jobs. The agent keeps it current while it works, and it closes itself once every item is done. If the agent leaves items open, the list stays visible without the working animation, and your next message hands the open items back to the agent until it finishes or clears them.
- Attachments: drop, paste or pick (the "+" button, then Files) images and files of any kind, up to 20 MB each. The agent gets the path of each stored copy and works on it with its tools and scripts, and whatever it makes from an attachment goes into the project. Models that take images see them; other models get a description from a separate vision model.
- Composer menus: the "+" button at the bottom left of the message box opens Files, Work in a project and Plan mode, with two tabs listing your skills and your MCP servers. Picking a skill or a ready server adds it as a chip in the bar of the message box, next to Plan, where hovering shows an x and a click removes it; when you send, the message tells the agent to load that skill, or to use that server's tools, for this request. Typing / at the start of a message or after a space opens the commands, filtered as you type: Compact, Auto-compact and Context limit for the current model, Archive, Pin and Fork chat, Memories (a small panel to view, add and delete saved memories), Initialize, Create GitHub repository, Plan mode and Visualize, which adds a chip that asks the agent to answer your next message with an interactive visualization. Up and Down move, Enter runs, Esc closes. While a menu is open, the task list and other cards above the message box move up out of its way; when there is not enough room above the message box, the menu and the cards get shorter and scroll on their own so nothing leaves the window.
- Talk to it while it works: Enter adds your message, attachments included, to the running turn at the next model round, and Tab queues it for after the turn. Queued messages sit in a panel on top of the message box, where you can steer, discard or pull one back into the box to edit it.
- Sub-agents for work that can run in parallel or would flood the main chat. Each one has a live transcript, and they report back when they are done. Agents in one chat know about each other: agents on the same topic split the work, share findings and ask each other directly, without ever waiting for an answer, and every message shows as a row in the receiving agent's transcript. Messages between agents arrive at once without a review; every task given to an agent passes the automatic review first. When an agent needs your approval, the question shows up above the message box and the agent is marked with a yellow dot, so you don't have to open each transcript. When you ask for it, the agent can take single tools away from a sub-agent, for example a worker that may edit files but not run commands; the agent's row in the Background Tasks panel shows which tools it lacks.
- A turn that works with tools or reasoning shows "Working for 12s" at its top while it runs. Once it is done, its reasoning, tool rows and in-between texts fold behind "Worked for 1m 5s", so the answer, images, visualizations, the plan, your steering messages and the file card stay in view; a click opens the work again.
- Tool calls and the reasoning between them form one closed line per stretch of work instead of a tall list of separate rows. While it runs, the line shows what happens right now (the current thought, "Thinking" or the running tool) with a running time; once done it says what the tools did, for example "Read 2 files, searched 1 string", with the total time. Opening it lists the tools and thoughts in order, one line per thought with a short description and its time that opens to the full reasoning. A long list scrolls inside a box of limited height and stays at its newest line unless you scrolled up or opened a row.
- While a model streams its reasoning, the collapsed reasoning row shows one or two sentences about what it is working on right now, written by a small side model in the interface language. A thought that ends before the first sentence arrives still gets one when it has a bit of text. When the reasoning ends, the row keeps a short description of what was thought about (that sentence, or else the last heading of the reasoning) with the time next to it, and reads "Thought for Xs" only when there is no description. This also works in sub-agent transcripts. Models that hide their reasoning show the plain "Thinking" label without a chevron, because there is no reasoning text to summarize or open.
- Undo on the newest turn's file card: it asks the agent to revert the changes it made in that turn and names the files that turn changed.
- Initialize from the composer's "/" menu: the agent inspects the project and writes or updates `AGENTS.md` with the build, test and run commands, the layout, the conventions and the gotchas it verified. It also works in a new chat of a project (the chat is created first and the request starts there) and needs a project.
- Create GitHub repository from the "/" menu (type /gitinit): the agent asks for the repository name, private or public, and whom to invite, then sets up git with a first commit and a .gitignore if needed, creates and pushes the repository with the GitHub CLI and sends the invitations. It needs the GitHub CLI (`gh`) signed in; without it the agent tells you how to set it up.
- Archive chats you are done with: Archive in a chat's menu in the sidebar, or the Archive chat command in the "/" menu, hides the chat from the sidebar lists, Pinned included. Archived at the bottom of the sidebar lists the archived chats; open one, restore it or delete it there. Sending a message or starting any other turn in an archived chat restores it to the lists. Search still finds archived chats and marks them.
- A built-in terminal and a browser the agent can drive. Every chat has its own browser tabs: the agent browses in the background without opening the Browser panel, agents of other chats cannot see or use those tabs, and opening the panel shows the current chat's tabs live so you can watch or take over. Models that take images look at the page themselves. The agent can also read the page's console (log messages, uncaught errors, failed requests) and evaluate side-effect-free JavaScript in the page to inspect its state.
- A Files panel (folder button in the title bar) shows the chat's project folder as a tree with a filter by file name, next to a read-only viewer with tabs, line numbers and syntax highlighting. It follows changes on disk while it is open, and clicking a file in a turn's file card opens it there with its current content. Each chat keeps its own Files panel and its own terminals: switching chats switches what the panels show and keeps the other chats' terminals running. In a Git repository the panel also shows the folder's Git state: changed files in the tree carry a letter in their status color (M modified, A added, D deleted, R renamed, C copied, T type changed, U untracked, ! conflict, S submodule), folders with changes inside get a dot, and ignored files are dimmed. A card above the tree shows the branch, how many commits are only local and how many are new on its upstream as of the last fetch, when that fetch was and the number of stash entries; a running merge, rebase, cherry-pick, revert or bisect gets its own row. While the panel is open, the app fetches the repository's primary remote in the background: when the repository is first shown, every 3 minutes while the window has focus, and on Refresh. It never fetches while the agent, a sub-agent or a background task works in the same repository (Refresh then fetches right after they finish), never over unencrypted http://, git:// or ftp://, and never when the repository's own configuration would start programs for the fetch or let it move local branches; the card then says "Automatic fetch off" and why. Missing Git credentials, a rejected SSH key, an unconfirmed SSH host or a missing remote show as a row in the card with the command to fix it where there is one, and offline shows next to the time. The panel title then becomes a switch between Files, Changes (with the number of changed files) and History. Changes lists the folder's conflicts, changed and untracked files in groups with their added and removed lines; a click opens the diff against the last commit for a modified, renamed, copied, type-changed or deleted file, and the file itself for an added, untracked or conflicted one. For a modified, renamed, copied or type-changed file the viewer has a File / Changes switch in its tab bar, and in File mode colored bars next to the line numbers mark added, changed and deleted lines; a deleted file opens straight in its diff, and binary files, changes to line endings only and conflicts get a one-line note. When the panel is narrower than 420 px it shows the list or tree and the viewer one at a time. History shows a commit graph of all branches, remote branches and tags across the full panel width, with the chosen commit's message and changed files below it; clicking a file opens its diff against the first parent right there. When Git is missing or too old, the repository belongs to another Windows user, the project folder is untracked inside a parent repository or Git reports an error, the card shows that instead, with the one action that helps (download Git, or the safe.directory command to copy). Refresh in the panel header reads the Git state and the folder again and fetches. Apart from the fetch, which only updates remote-tracking branches and tags, the panel only reads: it never commits, stages or changes your branches, programs named in the repository's own configuration (hooks, filters, fsmonitor, diff drivers, fetch programs) never run, and nothing from it goes to a model.
- Optional extras you turn on in the settings: web search through Tavily, image generation, memory across chats, skills and local MCP servers. With memory on, clear and explicit statements about how you work (for example "always answer in German") are saved from your messages automatically. Settings > Personalization > Memory lists them and you can remove any of them there. The "/" command Memories opens the same list in a small panel above the composer, where you can also delete a memory or add one yourself. A fact you discarded before is not saved again on its own; it waits under Memory review for Keep or Discard.
- Skills: built-in skills ship with the app and are on by default: one about VantheaX itself and `effects-lab` (group `design`), which builds visual effect pages and composed ads and checks them in a hidden browser window inside the app (the source lint needs Python) (they can be turned off, not removed). Your own skills live in the skills folder, one folder per skill with a `SKILL.md`, and can be sorted into group folders one level deep, for example `designs\glow\SKILL.md`.
- A soft notification sound while VantheaX is in the background: when the agent finishes or stops with an error, and when it asks you a question or needs your approval. Your own Stop and sub-agents stay silent. Turn it off under Settings > General > Notifications.
- English and German interface.

## GitHub

When the repository's primary remote is on GitHub, the Git card in the Files panel ends with a GitHub row: a lock (open for a public repository), the repository name, and the pull request and checks of the current branch. Clicking it shows the details: how the branch on GitHub compares with yours, the pull request with its reviews, each check with its duration and a link, and Open on GitHub. Public repositories on github.com need no sign-in: without a signed-in GitHub CLI they are read through GitHub's public API. Private repositories, GHE.com and GitHub Enterprise Server are read only through the GitHub CLI (`gh`) you are signed in to, and when it is signed in the app uses it for public repositories too: it sends read requests with `gh api` and never reads its token. The app has no GitHub sign-in of its own. When a repository can't be read, or GitHub's hourly limit for the public API is reached, the row offers `gh auth login` to copy, or the GitHub CLI download when `gh` is not installed or too old. The row updates about once a minute while the panel shows the repository and the window has focus, at once when the branch changes, and on Refresh; when GitHub has a commit on the branch that the last fetch did not bring, the background fetch runs right away. With GitHub data, the commit details in History also get Open on GitHub. Nothing from the GitHub row goes to a model.

## Permission modes

You choose how much the agent may do on its own, right in the message box.

- **Ask**: every command and every file write waits for you, except the screenshots the page check saves into the page's `_shots` folder.
- **Auto**: the agent just works on what you asked for. Every command, background task and MCP tool call first goes past an automatic review model. It judges how risky the step is, not whether you asked for that exact step, and reads your messages, your custom instructions, the project's `AGENTS.md` and `CLAUDE.md`, the earlier decisions in the chat, the scripts a command runs and what the files it touches contain. Ordinary development runs on its own: builds, tests, running the project's scripts and scripts the agent wrote, installing the project's dependencies, local git commits, starting and stopping the program being built, and creating, overwriting or deleting the agent's own files, temporary files and build output. The app marks every file an agent tool wrote and every file or folder that only came into being after the chat started ("created in this chat"), so the review recognizes the agent's own output whatever it is called. An older file the agent only edited keeps counting as data from before the chat. A step waits for your yes only when it is high risk and you didn't ask for it: deleting or overwriting data from before the chat that can't easily be restored (your documents, uncommitted or untracked work, files outside the project), installing software system-wide or other system changes, pushing, uploading or sending anything, running something downloaded, discarding git history, stopping processes the agent didn't start, or weakening security beyond a single run. Something your rules forbid, sending secrets or private files somewhere you didn't name, and serious damage like deleting the whole project are refused with the reason. Changes to `AGENTS.md` or `CLAUDE.md` also wait for your yes. Sub-agents follow the same rules. Reading a `.env` file, an API key, a token, a private key or a credential file is refused unless you allowed it in the chat. The agent then asks you, and after your yes the next attempt runs.
- **Full**: commands and writes run without asking. Commands are not reviewed in Full, so a command that reads `.env` or a key file runs without being stopped. When a file tool (read, search, list) names a secret file directly, the review still decides.

Saving or deleting a memory, installing a skill and adding an MCP server go past the same review in Auto and Full: what fits your messages runs, the rest waits for your yes or is refused with the reason. In Ask they always wait for you.

When you say no, that sticks: the review sees your earlier answers and refuses the same command, or another way to the same result, until you write something new in the chat. "Don't ask again for commands starting with ..." skips the question only where the review would have asked; a refusal by the review still stands. It works for the rest of the chat, also after a restart. A grant given for a PowerShell command does not cover Git Bash commands, and the other way round. If the review can't be reached or doesn't answer in time, you are asked instead of anything running unchecked. A question that comes from the review skips itself after 15 seconds without an answer, so a turn doesn't stall while you look away: the Skip button fills up, the step shows as skipped and the agent carries on without it. Start typing an answer and the countdown stops. A skipped question is not a no; the review treats it as unanswered. To let the chat and its sub-agents run without questions for ten minutes, pick "Full auto for 10 minutes" in the permission menu; the message box shows the time left and can end it early.

A short list of truly destructive commands (formatting a drive, deleting Windows or System32, wiping boot settings, deleting or moving VantheaX's own chats, media or settings) is blocked in every mode and can't be approved, whether the agent writes it for PowerShell or for Git Bash. If such a command is hidden inside a script the agent wants to run, you are asked first, even when the review would let it through.

## Building it

You need:

- Windows (built and used on Windows 10)
- Node.js 22.18 or newer (I use 24)
- An OpenRouter API key from https://openrouter.ai/keys
- Optionally a Tavily key if you want web search
- Optionally Git for Windows, for the agent's Git Bash tool and the Git view in the Files panel (2.33 or newer, 2.45 or newer for partial clones). It is found automatically; without it the agent only has PowerShell and the Files panel shows "Git is not installed" with a download link instead of a repository's Git state.
- Optionally the GitHub CLI (`gh`), signed in with `gh auth login`, for Create GitHub repository and for private repositories, GHE.com and GitHub Enterprise Server in the Files panel's GitHub row. The app looks for `gh.exe` on PATH.

Then:

```powershell
git clone https://github.com/7teb/VantheaV2.git
cd VantheaV2
npm ci
npm run package
```

The finished app lands in `outputs\electron\win-unpacked\`. Start `VantheaX.exe` from there. That folder contains everything the app needs, so you can move it wherever you like.

If you prefer an installer, run `npm run dist` instead. It writes `VantheaX Setup <version>.exe` to `outputs\electron\`.

This repository only holds what is needed to build the app. The dev server script and the test suite are not part of it, so `npm run dev` and `npm test` won't work here.

## First start

1. Open the settings with Ctrl+,.
2. Paste your OpenRouter key under General. It is stored encrypted through Windows' data protection.
3. If you want web search, add your Tavily key under Web search.
4. Pick a model in the message box, choose a project folder in the sidebar and start chatting.

The model list, including context and output limits, lives in `config/models.json`.

## Where your data goes

Settings, chats, attachments, generated images, memories, skills and agent transcripts are stored in `%APPDATA%\VantheaX\v2\`. Nothing leaves your machine except the requests to OpenRouter and to the services you turn on yourself, and, while the Files panel shows a Git repository, a git fetch of that repository's primary remote (the remote of the current branch's upstream, else origin, else the only remote), which uses your own Git setup and credentials; the app never reads them. When that remote is on GitHub, the app also sends read requests about that repository to GitHub's API: through your GitHub CLI login when `gh` is signed in to that host, otherwise without sign-in to the public API of github.com. For a remote on any other host, the app asks the GitHub CLI, if it is installed, whether it is signed in to that one host (`gh auth status --hostname <host>`), which contacts that host only when gh has an account there.
